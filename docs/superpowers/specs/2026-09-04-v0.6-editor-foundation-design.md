# Janus v0.6 — Editor Foundation Design

Date: 2026-09-04
Status: Implemented
Milestone: v0.6 Editor Foundation
Tracking: #29

## 1. Goal

v0.6 turns Janus from a disk-backed gameplay runtime into an authoring engine with a minimal but real visual Editor.

The target vertical slice is:

```text
JanusEditor
    ↓
Open SandboxProject
    ↓
ProjectSession
    ↓
EditorScene
    ↓
Hierarchy / Inspector / Asset Browser / Scene View
    ↓
Edit + Save
    ↓
Play
    ↓
Clone EditorScene -> RuntimeScene
    ↓
RuntimeSession + ScriptEngine
    ↓
Game View
    ↓
Stop
    ↓
Discard RuntimeScene
    ↓
Return to unchanged EditorScene
```

The milestone is complete when a user can launch `JanusEditor`, open the disk-backed Sandbox project, inspect and modify basic Scene state visually, save it, enter Play Mode, observe Lua gameplay in a Game View, stop the runtime, and continue editing without runtime state leaking back into authoring state.

This milestone intentionally does **not** introduce Reflection, CommandBus, Undo/Redo, MCP, Agent Activity, generic component metadata, prefab, physics, audio, animation, game UI, asset import pipelines, GPU ID picking, docking persistence, or production-grade project management.

---

## 2. Current baseline

v0.1-v0.5 already provide the runtime foundation v0.6 should build on:

- explicit `Application` ownership and cleanup;
- SDL3 Window + OpenGL context;
- `InputState` and frame timing;
- `Renderer2D` and opaque GPU handles;
- low-level framebuffer creation support in `RenderDevice`;
- ECS Registry with generational entities;
- `Scene`, hierarchy, persistent entity UUIDs, and components;
- disk-backed Scene serialization/deserialization;
- `AssetHandle`, `AssetRegistry`, `AssetService`, and runtime cache;
- `SceneRenderer`;
- Lua ScriptEngine with runtime-only instances and hot reload;
- a real `SandboxProject` fixture;
- Windows MSVC CI and automated regression coverage.

Important existing constraints remain unchanged:

- `ECS::Entity` is runtime identity only;
- UUID is persistent entity identity;
- AssetHandle is persistent resource identity;
- Scene files do not contain GPU handles, ECS indices, VM state, or absolute paths;
- Editor is a client of Engine public capability;
- Editor must not call OpenGL or SDL implementation APIs directly;
- Core must remain independent of Editor;
- no new graph of global `*Manager` singletons.

---

## 3. Central architectural decision

### 3.1 Application becomes the engine host, not the game runtime owner

The current v0.5 `Application` directly composes one Scene, one AssetService, one SceneRenderer, and one ScriptEngine and always advances gameplay before rendering.

That model is appropriate for Sandbox runtime but is too restrictive for an Editor.

v0.6 separates responsibilities conceptually as:

```text
Application
│
├── Platform
├── Window
├── GraphicsContext
├── Input
├── FrameClock
└── Renderer
        │
        ▼
ApplicationClient
        │
        ├── Sandbox Runtime Client
        └── Editor Client
                │
                ▼
           ProjectSession
                │
                ├── AssetRegistry
                ├── AssetService
                ├── EditorScene
                └── RuntimeSession?  (only while playing)
```

`Application` remains the composition root for platform and frame lifecycle.

It must no longer require every client to have an always-running ScriptEngine or one implicit gameplay Scene.

### 3.2 No Editor-specific code in Application

Do not add concepts such as:

```text
HierarchyPanel
InspectorPanel
SelectedEntity
EditorScene
PlayButton
ImGui
```

to `Application`.

The Editor is implemented as an `ApplicationClient` plus Editor-owned state.

### 3.3 Runtime convenience remains possible

The existing Sandbox must remain simple.

v0.6 may introduce a reusable runtime/session helper so Sandbox does not need to manually reproduce project loading, ScriptEngine start/update/stop, and rendering orchestration.

The architectural goal is shared engine capability, not duplicated bootstrap code.

## 4. ProjectSession

Introduce an Editor-owned `ProjectSession` or equivalent focused project context.

Conceptual state:

```cpp
struct ProjectSession
{
    std::filesystem::path projectRoot;
    std::filesystem::path currentScenePath;

    AssetRegistry assetRegistry;
    std::unique_ptr<AssetService> assetService;
    std::unique_ptr<Scene> editorScene;

    bool sceneDirty = false;
};
```

Exact type ownership may differ, but the responsibilities must remain explicit.

### Responsibilities

`ProjectSession` owns:

- project root;
- AssetRegistry loaded from project config;
- AssetService lifetime;
- the current authoring Scene;
- current Scene path;
- authoring dirty state;
- save/reload workflow.

It does **not** own:

- Window;
- GraphicsContext;
- platform input;
- ImGui global lifetime;
- Runtime Scene while not playing;
- ScriptEngine outside RuntimeSession;
- MCP or CommandBus.

### Project loading

The v0.6 project-open path can remain explicit/config-driven and does not need a full Create Project wizard.

The initial JanusEditor may accept:

```text
JanusEditor <project-root>
```

and default to `SandboxProject` in development builds.

A production `project.json` workflow is outside v0.6 unless required by the existing repository contract.

## 5. RuntimeSession and Play Mode isolation

Play Mode is the most important semantic boundary in v0.6.

### 5.1 State model

Editor owns one persistent authoring Scene:

```text
EditorScene
```

Pressing Play creates:

```text
RuntimeSession
├── RuntimeScene
└── ScriptEngine
```

The runtime Scene is never the same object as the editor Scene.

### 5.2 Lifecycle

```text
Edit
  │
  │ Play
  ▼
Clone EditorScene
  │
  ▼
Create RuntimeSession
  │
  ├── RuntimeScene
  └── ScriptEngine::Start
  │
  ▼
Playing
  │
  │ Stop
  ▼
ScriptEngine::Stop
  │
  ▼
Destroy RuntimeScene
  │
  ▼
Edit
```

Runtime Transform changes, Lua state, temporary entity mutations, and runtime-only caches are discarded on Stop.

### 5.3 Play state

Use an explicit small state model:

```cpp
enum class PlayState
{
    Editing,
    Playing,
    Paused
};
```

Pause may be implemented minimally in v0.6 if needed by the Editor toolbar, but Step Frame remains v0.9 scope.

### 5.4 ScriptEngine ownership

`ScriptEngine` belongs to `RuntimeSession`.

It must not execute against `EditorScene`.

This guarantees that simply opening an Editor project does not execute gameplay side effects.

## 6. Scene clone strategy

v0.6 requires semantic Scene cloning before Play Mode can be considered correct.

### 6.1 Required semantics

A clone must preserve authoring state:

- Scene metadata identity/name as appropriate;
- entity UUIDs;
- entity names;
- hierarchy;
- Transform local values;
- Camera authoring values;
- SpriteRenderer AssetHandles/properties;
- LuaScriptComponent AssetHandles/properties.

A clone must not copy runtime-only state as authoritative data:

- ECS index/generation identity;
- GPU handles;
- Lua instance state;
- world-transform cache as persistent truth;
- temporary editor selection;
- dirty flags as authoring semantics.

### 6.2 v0.6 implementation choice

Use an explicit `SceneCloner` public seam.

A first implementation may internally round-trip through the existing serializer/deserializer:

```text
Scene
  ↓
SceneSerializer::Serialize
  ↓
memory string
  ↓
SceneDeserializer::Deserialize
  ↓
Clone
```

This is acceptable in v0.6 because it provides deterministic semantics and exercises the persistence contract.

However, callers must depend on `SceneCloner`, not on the serialization trick directly.

That keeps a future in-memory component-wise clone optimization possible without changing Play Mode architecture.

### 6.3 Tests

Required:

- clone preserves supported authoring state;
- clone owns distinct ECS runtime entities;
- mutation of clone does not mutate source;
- hierarchy is independent;
- runtime ScriptEngine can mutate clone while source remains unchanged;
- failed clone returns no partial RuntimeScene.

## 7. Render target foundation

The existing RenderDevice can create a framebuffer, but Janus currently lacks a usable public render-target lifecycle.

v0.6 must add a backend-neutral render target abstraction before Scene View/Game View.

### 7.1 Required capability

Conceptually:

```text
CreateRenderTarget(width, height)
DestroyRenderTarget
ResizeRenderTarget
BeginRenderTarget
EndRenderTarget
GetColorTexture
```

Exact API placement may be `Renderer2D`, a focused `RenderTarget` wrapper, or a small renderer service, but it must satisfy:

- no OpenGL framebuffer IDs exposed above backend;
- deterministic RAII/explicit destruction;
- color texture can be consumed by Editor UI;
- resize recreates attachments safely;
- rendering can return to the default window target;
- viewport follows the target dimensions;
- resource destruction occurs before graphics context teardown.

### 7.2 Ownership

Editor owns:

```text
SceneViewRenderTarget
GameViewRenderTarget
```

They are runtime GPU resources and are never serialized.

### 7.3 ImGui texture presentation boundary

Dear ImGui's OpenGL backend may require a backend texture identifier.

Do not expose `GLuint` through Janus Engine public APIs just to satisfy ImGui.

Prefer an Editor/backend bridge that converts Janus texture presentation handles at the integration boundary.

The Engine-facing renderer remains backend-neutral.

### 7.4 Tests

Use FakeRenderDevice where possible:

- create/destroy;
- resize destroys/recreates resources correctly;
- begin/end target sequence;
- viewport changes;
- default target restoration;
- no leaked texture/framebuffer handles.

A narrow real OpenGL smoke path may supplement fake-device tests but must not replace them.

---

## 8. SceneRenderer evolution

The current `SceneRenderer::Render` always finds a CameraComponent from the Scene.

That is correct for Game View but wrong for Scene View.

v0.6 should introduce an explicit render request or equivalent separation.

Conceptual API:

```cpp
struct SceneRenderRequest
{
    Scene& scene;
    OrthographicCamera camera;
    Viewport viewport;
    RenderTargetHandle target;
};

Result<void> SceneRenderer::Render(const SceneRenderRequest& request);
```

The exact API may vary, but the following must be possible:

### Game View

```text
RuntimeScene
    ↓
Primary CameraComponent
    ↓
GameView RenderTarget
```

### Scene View

```text
EditorScene
    ↓
EditorCamera
    ↓
SceneView RenderTarget
```

Scene View must not mutate or depend on the Scene's gameplay camera.

A helper may still resolve the Scene primary camera for Game View.

---

## 9. Editor camera

The Scene View owns an independent editor camera.

Minimum state:

```cpp
struct EditorCameraState
{
    Vector2 position;
    f32 zoom;
};
```

v0.6 supports:

- pan;
- zoom;
- viewport resize;
- screen-to-world conversion.

Rotate camera is not required.

Input should only affect the editor camera while the Scene View is hovered/focused according to the chosen UI interaction rule.

---

## 10. Entity selection and picking

v0.6 uses CPU-side 2D picking.

Do not add GPU ID-buffer picking in this milestone.

### Flow

```text
Mouse position in Scene View
    ↓
Scene View local coordinates
    ↓
EditorCamera screen-to-world
    ↓
World point
    ↓
candidate SpriteRenderer bounds
    ↓
select top-most visible entity
```

Selection uses persistent entity UUID as Editor identity where practical.

The selected runtime ECS handle may be cached only transiently and must be validated before use.

### Ordering

When multiple sprites overlap, use deterministic ordering compatible with renderer semantics, at minimum:

1. layer;
2. stable fallback order.

Exact richer sort semantics may follow Renderer2D ordering.

### Limitations accepted in v0.6

- axis-aligned or simple transformed quad hit testing is sufficient;
- alpha-perfect picking is not required;
- non-sprite entities may only be selectable through Hierarchy;
- GPU picking is deferred.

---

## 11. Dear ImGui dependency

Use Dear ImGui for the first Editor UI.

### Boundary

Dear ImGui belongs to the `Editor` target/integration layer, not Core.

Engine public headers must not include `imgui.h`.

Recommended repository shape:

```text
Editor/
├── CMakeLists.txt
├── Main.cpp
├── EditorApplication.*
├── EditorContext.*
├── Panels/
│   ├── HierarchyPanel.*
│   ├── InspectorPanel.*
│   ├── SceneViewPanel.*
│   ├── GameViewPanel.*
│   ├── AssetBrowserPanel.*
│   └── ConsolePanel.*
└── Platform/
    └── ImGui integration if needed
```

Do not copy ImGui internals into Engine modules.

Pin the dependency version in CMake and document why it exists.

Docking may be used if the selected ImGui version/build strategy supports it cleanly, but persistent sophisticated workspace layout is not a v0.6 requirement.

---

## 12. EditorContext

Panels should not each invent direct ownership graphs.

Use one narrow Editor context/state object containing references to shared Editor services.

Conceptually:

```cpp
struct EditorContext
{
    ProjectSession* project;
    RuntimeSession* runtime;
    UUID selectedEntity;
    PlayState playState;
};
```

This is not a global singleton.

It is explicitly owned by `EditorApplication` and passed/referenced by panels.

Do not let panels directly own Scene, AssetService, or Renderer lifetimes.

---

## 13. Hierarchy panel

Minimum behavior:

- display the EditorScene hierarchy;
- select an entity;
- create a basic entity;
- delete selected entity;
- rename entity;
- display parent/child nesting.

Reparent drag/drop is desirable but may be deferred within v0.6 if it threatens the vertical slice.

All v0.6 modifications may call existing Scene mutation APIs directly because CommandBus is v0.7.

However, mutation calls must remain localized behind Editor action helpers rather than being spread arbitrarily across rendering code.

This reduces the migration cost when v0.7 routes edits through CommandBus.

---

## 14. Basic Inspector

Reflection is intentionally deferred to v0.7.

Therefore v0.6 Inspector may explicitly support the known built-in components:

- EntityIdentity name;
- Transform;
- SpriteRenderer;
- Camera;
- LuaScript.

The temporary rule is:

```text
manual component UI lives only in Editor
```

Do not introduce pseudo-reflection tables into Engine merely to avoid a small amount of v0.6 manual UI.

Do not claim this Inspector is the long-term component extensibility model.

### Mutation seam

Prefer focused Editor helper functions such as:

```text
EditorActions::SetTransform(...)
EditorActions::AddComponent(...)
EditorActions::RemoveComponent(...)
```

even if they currently call Scene directly.

v0.7 can replace their internals with CommandBus operations.

---

## 15. Asset Browser foundation

The current AssetRegistry supports lookup but not convenient enumeration.

v0.6 adds a read-only enumeration seam, for example:

```cpp
std::vector<AssetMetadata> GetAssets() const;
```

or a const iteration API.

Requirements:

- enumerate registered assets deterministically;
- show relative path;
- show type;
- expose AssetHandle;
- select an asset;
- allow basic assignment of a Texture AssetHandle to SpriteRenderer;
- allow basic assignment of a LuaScript AssetHandle to LuaScriptComponent.

Full importer/reimport/rename/delete workflows remain later scope.

The Editor must operate on registry metadata, not recursively guess engine assets from arbitrary filesystem files.

---

## 16. Scene dirty and save workflow

Authoring mutations mark the current EditorScene dirty.

Minimum behavior:

```text
Open Scene
  ↓
clean
  ↓
Edit
  ↓
dirty
  ↓
Save
  ↓
SceneSerializer::Save
  ↓
clean
```

RuntimeScene mutations never mark EditorScene dirty.

On save failure:

- keep dirty state;
- show a visible Editor error;
- do not discard authoring Scene;
- preserve existing atomic-file guarantees.

Unsaved-changes dialogs on application close are desirable but not required for the first vertical slice if clearly documented.

---

## 17. Console panel

v0.6 Console is intentionally small.

The current logger writes through spdlog sinks and does not yet expose a structured in-memory log stream suitable for Editor consumption.

Two acceptable approaches:

1. add a small Engine log capture sink/ring buffer with stable log record structure;
2. implement a minimal Editor console only after that seam exists.

Do not scrape stdout text.

The log record should remain useful for future v0.9 MCP log access:

```text
timestamp
level
category
message
```

Avoid building a Console-only telemetry architecture that later has to be replaced.

If this seam would expand v0.6 excessively, Console may initially show Editor-generated errors and a small captured Engine stream, with richer filtering deferred.

---

## 18. Main loop behavior

A conceptual Editor frame:

```text
Poll Platform Events
    ↓
Begin Input Frame
    ↓
Begin ImGui Frame
    ↓
Editor Update
    ├── Scene View camera input
    ├── authoring interactions
    └── toolbar/play state
    ↓
If Playing:
    ├── Lua hot reload
    └── ScriptEngine Update(RuntimeScene)
    ↓
Render Scene View(EditorScene, EditorCamera, SceneTarget)
    ↓
Render Game View(RuntimeScene or preview, GameCamera, GameTarget)
    ↓
Render ImGui
    ↓
Present
```

The exact order must ensure:

- gameplay does not run in Edit state;
- EditorScene is not changed by gameplay;
- render targets are complete before ImGui consumes their textures;
- input focus rules prevent gameplay/editor camera conflicts where practical.

Sandbox runtime may keep a simpler frame loop.

---

## 19. Error handling

Continue the existing explicit `Result/Error` model.

Recoverable Editor operations should surface errors in UI rather than crash:

- project load failure;
- Scene save failure;
- asset resolution failure;
- runtime clone failure;
- Lua compile/runtime failure;
- render target creation failure.

A runtime Lua failure during Play should stop or transition the RuntimeSession into a controlled failed state without destroying the EditorScene.

Do not use exceptions as routine Editor flow.

---

## 20. Testing strategy

Editor UI pixels are not the primary unit-test target.

Separate testable engine/editor logic from ImGui drawing.

### Required unit/integration coverage

#### Scene clone

- independent clone;
- component/hierarchy preservation;
- source unaffected by clone mutation.

#### RuntimeSession

- starts from clone;
- ScriptEngine runs only against runtime Scene;
- Stop destroys runtime state;
- repeated Play/Stop does not leak state;
- failure during start cleans up partially created runtime state.

#### Render target

- create/resize/destroy;
- target bind/unbind;
- color texture lifecycle;
- default target restoration.

#### ProjectSession

- project load;
- Scene load;
- dirty transition;
- successful save clears dirty;
- failed save preserves dirty.

#### Asset enumeration

- deterministic enumeration;
- type/path/handle preserved.

#### Editor selection logic

- screen/world conversion;
- simple sprite picking;
- deterministic overlap selection.

### End-to-end acceptance test

Prefer an integration test that can exercise the non-UI Editor session workflow with fake rendering:

```text
Load SandboxProject
    ↓
mutate EditorScene
    ↓
save
    ↓
Play
    ↓
Lua mutates RuntimeScene
    ↓
Stop
    ↓
EditorScene retains authoring value
```

Manual Editor verification supplements, but does not replace, automated coverage.

## 21. Dependency and module rules

Allowed:

```text
Editor -> Engine public API
Editor -> Dear ImGui integration
RuntimeSession -> Scene / Asset / Scripting
SceneRenderer -> Renderer public API
OpenGL backend -> OpenGL
```

Forbidden:

```text
Engine -> Editor
Core -> ImGui
Scene -> ImGui
Editor panel -> OpenGL
Editor panel -> SDL implementation
Editor -> ECS internal storage bypass for normal operations
RuntimeScene == EditorScene
ScriptEngine running on EditorScene
```

Direct Scene component mutation is a temporary v0.6 concession only for Editor authoring and must remain localized for v0.7 migration.

## 22. v0.7 compatibility boundary

v0.7 introduces Reflection + Command.

v0.6 must deliberately leave a migration seam.

### What v0.6 may do

```text
Hierarchy UI
    ↓
EditorActions
    ↓
Scene public API

Inspector UI
    ↓
EditorActions
    ↓
known component mutation
```

### What v0.7 replaces

```text
EditorActions
    ↓
CommandBus
    ↓
Reflection-backed component/property capability
    ↓
Scene
```

Panels should not need to be rewritten from scratch.

Do not implement an incomplete CommandBus in v0.6.

Do not create Editor-only reflection metadata that competes with the v0.7 design.

## 23. Implementation split

After this design lands, implementation should proceed in dependency order.

### A. Editor host and session foundation

- pin Dear ImGui;
- add `JanusEditor` target;
- refactor Application/runtime composition so gameplay is optional;
- introduce ProjectSession;
- preserve Sandbox behavior.

### B. Scene clone and RuntimeSession

- add SceneCloner seam;
- create isolated RuntimeScene;
- move ScriptEngine ownership into runtime session;
- Play/Stop lifecycle tests.

### C. Renderer render-target foundation

- backend-neutral render target lifecycle;
- framebuffer bind/unbind;
- resize;
- color texture presentation;
- fake-device tests.

### D. Scene/Game view rendering

- explicit camera render path;
- EditorCamera;
- Scene View;
- Game View;
- viewport resize.

### E. Hierarchy, selection, and basic Inspector

- hierarchy tree;
- selected UUID;
- CPU sprite picking;
- entity create/delete/rename;
- manual built-in component Inspector.

### F. Asset Browser and save workflow

- registry enumeration;
- asset selection/assignment;
- dirty tracking;
- Scene save/reload.

### G. Editor vertical-slice completion

- Play toolbar;
- Lua gameplay in Game View;
- controlled runtime errors;
- Console foundation;
- README/roadmap/AGENTS updates;
- end-to-end regression verification.

These implementation units should become separate GitHub issues/PRs rather than one monolithic Editor PR.

## 24. Acceptance criteria

v0.6 is complete only when all of the following hold.

### Authoring

A user can:

```text
Launch JanusEditor
↓
Open SandboxProject
↓
See Scene hierarchy
↓
Select an entity
↓
Edit Transform
↓
Assign supported asset handles
↓
Save Scene
```

without modifying C++ source.

### Scene View

- independent Editor camera;
- pan;
- zoom;
- sprite rendering;
- entity selection;
- basic move/edit through Inspector;
- grid if simple to implement in the render/UI layer.

### Game View / Play Mode

```text
EditorScene
↓ Clone
RuntimeScene
↓
ScriptEngine
↓
Lua gameplay
↓
Game View RenderTarget
```

Stop discards RuntimeScene and returns to unchanged EditorScene.

### Engineering

- no OpenGL/SDL implementation types leak into Editor panel APIs;
- Engine has no dependency on Editor/ImGui;
- runtime/editor ownership is explicit;
- all v0.1-v0.5 regression tests remain green;
- new non-UI v0.6 logic has automated coverage;
- Windows MSVC configure/build/CTest passes;
- documentation matches implementation.

## 26. Key risks

### Risk 1: Application becomes an Editor god object

Mitigation: keep Application responsible for platform/frame hosting; move project/play state into explicit sessions.

### Risk 2: Editor directly edits RuntimeScene

Mitigation: RuntimeScene exists only inside RuntimeSession and is always cloned from EditorScene.

### Risk 3: ImGui leaks backend types upward

Mitigation: isolate backend presentation conversion at Editor integration boundary; never expose GLuint through normal Engine APIs.

### Risk 4: v0.6 builds disposable Inspector architecture

Mitigation: manual component UI is explicitly temporary and localized; mutations go through a narrow EditorActions seam.

### Risk 5: UI work hides missing engine capability

Mitigation: implement Scene clone and render target foundations before most panels.

### Risk 6: v0.6 expands into v0.7

Mitigation: no Reflection/CommandBus implementation; preserve only migration seams.

---

## 27. Final architecture after v0.6

```text
                           Janus Engine
                                ▲
               ┌────────────────┴───────────────┐
               │                                │
          JanusSandbox                     JanusEditor
               │                                │
        Runtime Session                   EditorApplication
                                                │
                                         ProjectSession
                                                │
                              ┌─────────────────┴──────────────┐
                              │                                │
                         EditorScene                     RuntimeSession?
                              │                                │
                       Scene View                         RuntimeScene
                       EditorCamera                           │
                              │                           ScriptEngine
                              │                                │
                              └────────────┬───────────────────┘
                                           │
                                      SceneRenderer
                                           │
                                ┌──────────┴──────────┐
                                │                     │
                         Scene RenderTarget    Game RenderTarget
                                │                     │
                                └──────────┬──────────┘
                                           │
                                        ImGui UI
```

v0.6 establishes the Human-facing authoring loop.

v0.7 can then place Reflection and CommandBus beneath those Editor actions, and v0.8 can attach MCP to the same capability layer without making MCP depend on Editor implementation.

# Janus v0.6 — Visual Editor Stage Design

Date: 2026-09-05
Status: Proposed
Milestone: v0.6 Editor Foundation
Depends on: #31, #32
Tracking: #33, #34, #35

## 1. Stage Goal

The first half of v0.6 established ownership and runtime isolation:

```text
Application
    ↓
JanusEditor
    ↓
ProjectSession
    ├── EditorScene
    └── RuntimeSession?
            ├── RuntimeScene
            └── ScriptEngine
```

This stage turns that correct ownership model into a usable visual authoring loop.

The target is not “add several ImGui windows”.

The target is:

```text
EditorScene
    ├── Scene View  -> independent Editor Camera
    └── Hierarchy / Inspector
               │
               │ Play
               ▼
          RuntimeScene
               │
               └── Game View -> gameplay Camera
```

At the end of this stage, JanusEditor must be able to show the authoring Scene, show the game output, select an Entity, and edit basic built-in components while preserving the Edit/Play isolation already established by #32.

---

## 2. Scope

This design covers:

- #33 renderer render-target lifecycle;
- #34 Scene View and Game View render path;
- #35 Hierarchy, selection, and basic Inspector;
- Editor-local viewport input;
- Editor camera;
- CPU 2D picking;
- EditorContext / EditorActions seams.

It does not cover:

- Asset Browser and save workflow (#36);
- final Console/E2E/documentation closeout (#37);
- Reflection;
- CommandBus;
- Undo/Redo;
- MCP;
- generic input mapping;
- GPU ID picking;
- prefab;
- physics/audio/animation/game UI.

---

## 3. Current Baseline

Current `main` already has:

- `ApplicationExecutionMode::ClientDriven`;
- `JanusEditor`;
- Dear ImGui integration;
- `ProjectSession`;
- `EditorScene`;
- `SceneCloner`;
- `RuntimeSession`;
- `RuntimeScene`;
- runtime-only `ScriptEngine`;
- Play/Stop isolation tests;
- `Renderer2D`;
- low-level framebuffer creation in `RenderDevice`;
- `SceneRenderer` that currently resolves a Scene Camera internally.

The key remaining gaps are:

1. framebuffer creation is not a complete render-target lifecycle;
2. `Renderer2D` cannot render a frame into an offscreen target;
3. `SceneRenderer` is hard-wired to a Scene Camera;
4. Editor has no independent Scene camera;
5. Editor has no shared selection state;
6. Editor has no viewport-sized image presentation path;
7. Core Input currently has keyboard only.

---

# Part A — Render Target Foundation (#33)

## 4. Render target is a Renderer capability

Do not expose raw framebuffer operations to Editor panels.

The public rendering flow should be:

```text
Editor / SceneRenderer
        ↓
Renderer2D
        ↓
RenderTargetHandle
        ↓
RenderDevice
        ↓
OpenGL framebuffer + color texture
```

Editor code must not call:

```text
glBindFramebuffer
glFramebufferTexture2D
GLuint
GL_FRAMEBUFFER
```

---

## 5. RenderTarget data model

Introduce an opaque public handle:

```cpp
struct RenderTargetHandle
{
    u32 value = 0;
};
```

and a description:

```cpp
struct RenderTargetDesc
{
    u32 width = 0;
    u32 height = 0;
};
```

Internally, Renderer2D owns records similar to:

```cpp
struct RenderTargetRecord
{
    FramebufferHandle framebuffer;
    TextureHandle colorTexture;
    Viewport viewport;
};
```

The record is runtime-only and is never serialized.

---

## 6. Prefer frame-target integration over manual bind/unbind at call sites

A raw API such as:

```text
BeginRenderTarget
BeginFrame
EndFrame
EndRenderTarget
```

creates an unnecessary state-leak risk when an error occurs between Begin and End.

Instead evolve Renderer2D toward one frame descriptor:

```cpp
struct RenderFrameDesc
{
    OrthographicCamera camera;
    Viewport viewport;
    RenderTargetHandle target; // invalid => default window framebuffer
    Color clearColor = Color::White();
};
```

Conceptual API:

```cpp
Result<void> BeginFrame(const RenderFrameDesc& desc);
Result<void> EndFrame();
```

`BeginFrame` is responsible for:

- validating the target;
- binding target or default framebuffer;
- applying viewport;
- resetting queue/statistics;
- applying camera;
- applying shader.

`EndFrame` is responsible for:

- clearing;
- flushing;
- restoring the default framebuffer after offscreen rendering;
- clearing active-frame state even when flush fails.

This gives one ownership boundary for render state.

The old `BeginFrame(camera)` API may be retained temporarily as a compatibility wrapper if that keeps the PR focused.

---

## 7. Low-level RenderDevice changes

RenderDevice needs only the backend operations required by Renderer2D:

```cpp
virtual Result<void> BindFramebuffer(FramebufferHandle) = 0;
virtual void BindDefaultFramebuffer() = 0;
```

Framebuffer creation/destruction remain existing capabilities.

OpenGL implements these internally through `glBindFramebuffer`.

No backend-specific type escapes the backend.

---

## 8. Color attachment allocation

Offscreen targets require an empty RGBA8 texture.

Current texture creation semantics should explicitly allow:

```text
width > 0
height > 0
data == nullptr
dataSize == 0
```

to mean:

> allocate GPU storage without initial CPU pixels.

This is valid renderer behavior and should not be implemented as an Editor-only special case.

---

## 9. Transactional resize

Viewport resizing is frequent during Editor use.

`ResizeRenderTarget` must be transactional:

```text
old target resources remain valid
        ↓
create new color texture
        ↓
create new framebuffer
        ↓
if success:
    swap record
    destroy old framebuffer
    destroy old texture
else:
    destroy partial new resources
    retain old record
```

A failed resize must not turn a previously valid Scene View into a broken target.

Do not resize when requested dimensions are zero.

A collapsed/hidden panel should simply skip target rendering.

---

## 10. Required Renderer2D API

Recommended minimum:

```cpp
Result<RenderTargetHandle> CreateRenderTarget(
    const RenderTargetDesc& desc);

Result<void> ResizeRenderTarget(
    RenderTargetHandle handle,
    u32 width,
    u32 height);

Result<void> DestroyRenderTarget(
    RenderTargetHandle handle);

Result<TextureHandle> GetRenderTargetColorTexture(
    RenderTargetHandle handle) const;
```

Invalid handles return explicit `Result/Error`.

Destroying an active target/frame is an `InvalidState` error rather than silently invalidating renderer state.

---

## 11. ImGui texture presentation bridge

A Janus `TextureHandle` is not an OpenGL texture object ID.

Therefore this is wrong:

```cpp
ImGui::Image((ImTextureID)textureHandle.value, ...);
```

Introduce a narrow presentation seam.

Conceptually:

```cpp
struct TexturePresentationHandle
{
    uintptr_t value = 0;
};
```

Renderer backend maps:

```text
TextureHandle
    ↓
backend texture object
    ↓
TexturePresentationHandle
```

Editor/ImGui integration converts only this presentation handle to the ImGui backend representation.

Rules:

- no `GLuint` in Editor panel interfaces;
- no ImGui type in Engine headers;
- presentation handles are runtime-only;
- this seam is not serialization identity;
- AssetHandle and TextureHandle semantics remain unchanged.

Keep the bridge in an Editor integration file such as:

```text
Editor/Platform/ImGuiTextureBridge.*
```

---

## 12. #33 tests

FakeRenderDevice should record:

- framebuffer creation;
- framebuffer destruction;
- framebuffer binding;
- default framebuffer restoration;
- texture creation;
- texture destruction;
- viewport changes.

Required cases:

1. create target creates one color texture and one framebuffer;
2. target frame binds framebuffer;
3. EndFrame restores default framebuffer;
4. resize replaces resources;
5. failed resize preserves old resources;
6. zero-size resize is rejected or skipped by the caller contract;
7. target destruction destroys framebuffer before color texture;
8. invalid target operations return explicit errors;
9. default-window rendering still behaves exactly as before.

---

# Part B — Scene View / Game View (#34)

## 13. SceneRenderer must stop owning camera policy

Current `SceneRenderer::Render` always searches the Scene for a CameraComponent.

That combines two responsibilities:

```text
choose camera
render scene
```

The Scene View needs an Editor Camera that is not a Scene entity.

Therefore introduce an explicit render request:

```cpp
struct SceneRenderRequest
{
    Scene& scene;
    AssetService& assets;
    Renderer2D& renderer;
    OrthographicCamera camera;
    Viewport viewport;
    RenderTargetHandle target;
};
```

Primary API:

```cpp
Result<void> Render(const SceneRenderRequest& request);
```

A helper may remain for game-camera resolution:

```cpp
Result<OrthographicCamera> BuildPrimaryCamera(Scene& scene);
```

or a compatibility wrapper may resolve the Scene primary camera and delegate to the explicit request.

The important architectural rule is:

> Rendering a Scene no longer implies choosing its camera.

---

## 14. Scene View source is always EditorScene

Even while Play Mode is running:

```text
Scene View
    ↓
EditorScene
```

This makes the semantic boundary obvious.

v0.6 does not switch Scene View to RuntimeScene.

The Editor may continue inspecting authoring state while the game runs, but authoring mutation is read-only during Play Mode in this milestone.

This avoids ambiguous “edit runtime or edit source?” behavior before Command/transaction semantics exist.

---

## 15. Game View source depends on Play state

Define:

### Edit mode

```text
Game View
    ↓
EditorScene
    ↓
primary CameraComponent
```

This is a non-scripted preview.

### Play mode

```text
Game View
    ↓
RuntimeScene
    ↓
primary CameraComponent
```

Lua only mutates RuntimeScene.

Stop immediately returns Game View to the EditorScene camera preview.

This makes Game View useful before and during Play without violating scene isolation.

---

## 16. EditorCamera

Scene View owns a standalone camera state:

```cpp
class EditorCamera
{
public:
    Vector2 position;
    f32 zoom = 1.0f;

    void Pan(Vector2 deltaWorld);
    void Zoom(f32 wheelDelta);

    Vector2 ScreenToWorld(
        Vector2 viewportPoint,
        Viewport viewport) const;

    OrthographicCamera ToRenderCamera() const;
};
```

No Scene entity is created for this camera.

No CameraComponent is modified when the user pans the Scene View.

Minimum behavior:

- middle-mouse or equivalent drag pans;
- wheel zooms;
- zoom is clamped to a safe positive range;
- screen-to-world is deterministic and unit tested;
- viewport resize does not change world camera position.

Rotation is not required.

---

## 17. Editor-local viewport input

Do not add Engine-wide mouse input solely for v0.6 Editor.

Current Core Input is keyboard-only.

For Scene View, use an Editor-local value captured from ImGui:

```cpp
struct ViewportInput
{
    Vector2 localMouse;
    Vector2 dragDelta;
    f32 wheelDelta = 0.0f;
    bool hovered = false;
    bool focused = false;
    bool primaryClicked = false;
    bool panDragging = false;
};
```

This has two advantages:

1. viewport-local coordinates and hover/focus already come from the UI layout;
2. Editor mouse behavior remains independent from future game Input Mapping.

Non-ImGui logic consumes `ViewportInput`, which keeps EditorCamera and picking testable.

Future v0.10 game mouse/input mapping does not need to reuse this Editor-specific type.

---

## 18. Viewport resize ordering

ImGui viewport content size is dynamic.

The correct frame order is important because resizing a render target changes the color texture presented by ImGui.

Per viewport:

```text
Begin ImGui panel
    ↓
read available content size
    ↓
if valid size changed:
    resize RenderTarget first
    ↓
get current presentation texture
    ↓
emit ImGui::Image
    ↓
capture viewport input
```

Then, before final `ImGui_ImplOpenGL3_RenderDrawData`:

```text
update RuntimeSession
render Scene View target
render Game View target
render ImGui draw data
present window
```

Do not register an ImGui image using an old texture and then destroy that texture later in the same frame.

That would leave ImGui draw data referencing a dead backend texture.

---

## 19. Editor frame orchestration

Target frame structure:

```text
Application PollEvents / InputState
        ↓
ImGui NewFrame
        ↓
Toolbar
        ├── Play
        └── Stop
        ↓
Panel layout
        ├── Scene View size + ViewportInput
        └── Game View size
        ↓
Update EditorCamera
        ↓
if Playing:
    ProjectSession::UpdateRuntime(dt)
        ↓
Render Scene View
    EditorScene + EditorCamera + SceneTarget
        ↓
Render Game View
    Edit: EditorScene + Game Camera
    Play: RuntimeScene + Game Camera
        ↓
Render default Editor window background if required
        ↓
ImGui::Render
        ↓
ImGui backend draw
        ↓
Present
```

Runtime Lua errors should be surfaced to Editor state and stop the runtime session rather than terminating the entire JanusEditor process.

Rich Console presentation remains #37.

---

## 20. Editor View ownership

Recommended Editor-side state:

```text
EditorApplication
├── ProjectSession
├── SceneRenderer
├── EditorContext
├── SceneViewState
│   ├── EditorCamera
│   └── RenderTargetHandle
└── GameViewState
    └── RenderTargetHandle
```

Panels may render UI around these objects but do not own:

- ProjectSession;
- EditorScene;
- RuntimeScene;
- AssetService;
- Renderer2D.

This prevents panel lifetime from becoming engine lifetime.

---

## 21. #34 tests

Required non-ImGui tests:

### EditorCamera

- pan;
- zoom clamp;
- screen center maps to camera position;
- screen/world conversion across viewport sizes.

### SceneRenderer

- explicit Editor camera does not require CameraComponent;
- game-camera helper selects primary camera;
- explicit target/viewport reaches Renderer2D correctly;
- Editor camera does not mutate CameraComponent.

### view source policy

- Edit Game View resolves EditorScene;
- Play Game View resolves RuntimeScene;
- Scene View remains EditorScene during Play;
- Stop returns Game View source to EditorScene.

Manual verification:

- resize Scene View repeatedly;
- pan/zoom without moving gameplay camera;
- Play causes Player Lua motion only in Game View;
- Stop returns to authoring state.

# Part C — Hierarchy / Selection / Basic Inspector (#35)

## 22. EditorContext

Introduce one explicit shared Editor state object.

Minimum conceptual form:

```cpp
struct EditorSelection
{
    std::optional<UUID> entity;
};

struct EditorContext
{
    ProjectSession* project = nullptr;
    EditorSelection selection;
};
```

Do not make this a singleton.

Selection identity is UUID, not `ECS::Entity`.

Whenever a panel needs the current runtime ECS entity it resolves:

```text
selected UUID
    ↓
EditorScene::FindEntity
    ↓
validated ECS::Entity
```

This survives ECS handle churn and aligns with future Command/MCP identity.

---

## 23. Selection always targets EditorScene in v0.6

Hierarchy and Scene View select authoring entities.

Even while Playing:

```text
selection UUID
    ↓
EditorScene
```

Inspector displays EditorScene authoring state.

During Play, mutation widgets are disabled/read-only.

This deliberately avoids a temporary “runtime Inspector” semantics that would conflict with v0.7/v0.9 plans.

---

## 24. CPU 2D picking

Do not implement GPU ID picking.

Flow:

```text
ViewportInput.localMouse
    ↓
EditorCamera::ScreenToWorld
    ↓
world point
    ↓
EditorScene Sprite candidates
    ↓
point-in-transformed-quad
    ↓
top-most candidate
    ↓
selected UUID
```

For a Sprite candidate:

1. subtract world position;
2. rotate point by negative world rotation;
3. account for world scale;
4. compare against half sprite size.

This handles rotated/scaled 2D sprites without an alpha test.

Do not perform alpha-perfect picking.

---

## 25. Picking order

Minimum deterministic rule:

1. highest Sprite layer wins;
2. same layer uses a stable Scene iteration fallback.

This is consistent with the existing v0.6 design and avoids introducing a new render-order model.

A future explicit sort-order/entity-order property may replace this.

---

## 26. Hierarchy panel

Minimum behavior:

- display root entities;
- recursively display children;
- preserve hierarchy nesting;
- select entity;
- create Entity;
- delete selected Entity;
- rename Entity.

Do not require drag/drop reparenting to close #35.

Reparenting can be added only if the core vertical slice is already green.

---

## 27. EditorActions seam

Do not place mutation logic directly inside ImGui widget code.

Introduce a temporary facade:

```cpp
class EditorActions
{
public:
    Result<UUID> CreateEntity(...);
    Result<void> DeleteEntity(UUID);
    Result<void> RenameEntity(UUID, std::string);

    Result<void> SetTransform(...);
    Result<void> AddSpriteRenderer(...);
    Result<void> RemoveSpriteRenderer(...);
    Result<void> SetCamera(...);
    Result<void> SetLuaScript(...);
};
```

In v0.6 it can call Scene/component APIs directly.

In v0.7 its internals become:

```text
EditorActions
    ↓
CommandBus
    ↓
Reflection-backed mutation
```

Panels should not need a full rewrite.

---

## 28. Play-mode mutation rule

`EditorActions` must reject authoring mutation while a RuntimeSession is active.

Use an explicit error such as `InvalidState`.

UI should disable mutation widgets during Play, but the action layer must enforce the rule too.

This prevents correctness from depending on UI state.

---

## 29. Basic Inspector

Manually support only:

- Entity name;
- Transform;
- SpriteRenderer;
- Camera;
- LuaScript.

Required component policy:

### Always-present

- EntityIdentity;
- Transform;
- Hierarchy.

Do not expose Remove for required components.

### Optional

- SpriteRenderer;
- Camera;
- LuaScript.

Allow add/remove where valid.

Do not create a generic metadata/reflection system in #35.

---

## 30. Transform editing

Inspector edits local authoring values:

```text
position
rotationRadians
scale
```

World transform fields remain derived/read-only.

Do not write:

```text
worldPosition
worldRotationRadians
worldScale
dirty cache
```

directly from Inspector.

The renderer/transform traversal remains responsible for derived world state.

---

## 31. Selection lifecycle

Clear selection when:

- selected Entity is deleted;
- a new project/Scene is loaded;
- selected UUID no longer resolves.

Do not clear selection merely because Play starts or stops.

The UUID remains an authoring identity.

---

## 32. #35 tests

Required:

### selection

- selection stores UUID;
- UUID resolves to current EditorScene ECS entity;
- stale/deleted UUID clears safely.

### picking

- center hit;
- miss;
- translated sprite;
- scaled sprite;
- rotated sprite;
- disabled sprite ignored;
- invalid texture/sprite policy is deterministic;
- higher layer wins.

### EditorActions

- create;
- delete;
- rename;
- Transform edit;
- optional component add/remove;
- required components cannot be removed;
- mutation rejected during Play.

### hierarchy

Test traversal/order logic independently from ImGui rendering where possible.

# Part D — Architecture After This Stage

## 33. Target ownership graph

```text
Application
│
└── JanusEditor
    │
    └── EditorApplication
        │
        ├── ProjectSession
        │   ├── AssetRegistry
        │   ├── AssetService
        │   ├── EditorScene
        │   └── RuntimeSession?
        │       ├── RuntimeScene
        │       └── ScriptEngine
        │
        ├── SceneRenderer
        │
        ├── EditorContext
        │   └── selected Entity UUID
        │
        ├── SceneViewState
        │   ├── EditorCamera
        │   └── Scene RenderTarget
        │
        └── GameViewState
            └── Game RenderTarget
```

Renderer path:

```text
Scene
  ↓
SceneRenderer
  ↓ explicit camera
Renderer2D
  ↓ RenderFrameDesc
RenderTargetHandle
  ↓
RenderDevice
  ↓
OpenGL
```

Keep implementation order strict:

```text
#33 RenderTarget
        ↓
#34 SceneRenderer explicit camera
        ↓
#34 Scene View + Game View
        ↓
#35 EditorContext + EditorActions
        ↓
#35 Hierarchy
        ↓
#35 CPU Picking
        ↓

        ↓
```

Do not begin Scene View before render targets are complete.

## 36. Stage acceptance path

The stage is complete when this path works:

```text
Launch JanusEditor
    ↓
Open SandboxProject
    ↓
Scene View shows EditorScene
    ↓
pan / zoom Scene View
    ↓
Game View shows gameplay camera preview
    ↓
select Player from Hierarchy
    ↓
select Player from Scene View
    ↓
Inspector shows Transform / Sprite / LuaScript
    ↓
edit Transform in Edit mode
    ↓
Play
    ↓
Inspector becomes read-only
    ↓
RuntimeScene clone starts
    ↓
Lua moves Runtime Player in Game View
    ↓
Scene View remains EditorScene
    ↓
Stop
    ↓
RuntimeScene discarded
    ↓
authoring Player remains at edited authoring position
```

Saving that authoring change belongs to #36.

---

## 37. Non-goals / Stop Conditions

If implementation work starts pulling in any of the following, stop and defer:

- generic Reflection metadata;
- Undo/Redo;
- Command history;
- runtime Inspector mutation;
- GPU picking;
- gizmo framework;
- docking persistence;
- asset thumbnail generation;
- file drag/drop import;
- generalized mouse/game input mapping;
- multi-scene Editor;
- prefab editing.

The purpose of this stage is to establish a clean visual authoring architecture, not to imitate a mature commercial Editor feature-for-feature.

# Janus v0.5 — Lua Gameplay Runtime Design

Date: 2026-09-03
Status: Proposed
Milestone: v0.5 Lua Gameplay Runtime

## 1. Goal

v0.5 turns Janus from a persisted/renderable world runtime into a gameplay runtime whose behavior can be authored without recompiling the C++ engine.

The target vertical slice is:

```text
Persistent Project
    ↓
Battle.scene + AssetRegistry
    ↓
LuaScriptComponent -> Script AssetHandle
    ↓
ScriptEngine
    ↓
Lua VM + per-entity ScriptInstance
    ↓
Entity / Transform / Input bindings
    ↓
OnCreate / OnUpdate / OnDestroy
    ↓
SceneRenderer
```

The milestone is complete when a disk-backed Sandbox Scene can attach a Lua script to an entity, reopen the project, run the script, move the entity from Lua using input, hot-reload the script at a basic file level, and shut down cleanly.

This milestone intentionally does **not** introduce Editor, Reflection, CommandBus, MCP, prefab, physics, animation, audio, UI, networking, coroutine scheduling, or a general plugin system.

---

## 2. Current baseline

v0.4 already provides the persistence and runtime seams v0.5 should build on:

- persistent `UUID` identity;
- `AssetHandle` and `AssetRegistry`;
- project-relative asset paths;
- disk-backed startup Scene;
- Scene serialization/deserialization;
- `AssetService` and cache ownership;
- `Application` as the composition/bootstrap root;
- `InputState` per frame;
- `SceneRenderer` after world update;
- explicit `Result/Error` paths for recoverable failures.

Important existing constraints:

- `ECS::Entity` is runtime-only and must not cross persistence boundaries;
- Scene identity is UUID-based;
- Engine modules remain free of game-specific behavior;
- Sandbox is a client of public Engine APIs;
- no new global `*Manager` graph should be introduced.

## 3. Dependency decision

### 3.1 Lua version

Pin **Lua 5.4.9** for v0.5.

Source:

```text
https://www.lua.org/ftp/lua-5.4.9.tar.gz
```

SHA-256:

```text
2335b6c582a52654f94612bf10d2f4672805d05329aa6568b1d8cd9e5c6fb8e6
```

Lua 5.5 exists, but v0.5 deliberately chooses the mature 5.4 line. Janus does not need 5.5-specific language features for this milestone, and the narrower compatibility surface is more valuable than adopting the newest language release immediately.

### 3.2 Binding approach

Use the **Lua C API directly** behind Janus-owned wrappers. Do not add sol2/LuaBridge in v0.5.

Reasons:

1. Janus is an engine-learning and runtime-architecture project; the Lua/C++ boundary is itself valuable implementation knowledge.
2. A thin owned layer makes stack discipline, error translation, userdata lifetime, and binding policy explicit.
3. It avoids coupling the public scripting architecture to a third-party template binding library.
4. Janus only needs a small binding surface in v0.5: entity identity, transform mutation, and input queries.
5. Future binding helpers can still be introduced behind the same `ScriptEngine` boundary if the manual surface becomes too expensive.

Lua headers and `lua_State*` must remain private implementation details. Public Janus headers must not require consumers to include Lua headers.

## 4. Module layout

Add a focused scripting module:

```text
Engine/Scripting/
├── LuaVirtualMachine.h/.cpp
├── LuaStackGuard.h
├── LuaBinding.h/.cpp
├── ScriptEngine.h/.cpp
├── ScriptInstance.h/.cpp
└── ScriptTypes.h
```

Public API should stay small. `LuaVirtualMachine`, raw Lua helpers, and most binding code should remain private implementation detail where possible.

Layering:

```text
Core
  ↑
Asset   Scene   Input
   \      |      /
    \     |     /
      Scripting
          ↑
     Application
```

Rules:

- Core never depends on Scripting.
- Renderer never depends on Scripting.
- Scene data may define `LuaScriptComponent`, but Scene does not execute Lua itself.
- Scripting may depend on Scene, Asset, Input, and Core.
- Application owns lifecycle composition.
- Sandbox does not call Lua C API.

## 5. Script asset model

Extend `AssetType` with:

```cpp
AssetType::LuaScript
```

Registry JSON uses:

```json
{
  "handle": "...",
  "type": "lua-script",
  "path": "Scripts/PlayerController.lua"
}
```

Add a script source loading path that:

- resolves through `AssetRegistry`;
- requires `AssetType::LuaScript`;
- accepts only project-relative registered paths;
- reads UTF-8/source bytes from disk;
- returns explicit `Result/Error` failures;
- does not expose an absolute path to Scene data.

The runtime may internally retain the resolved filesystem path and `last_write_time` for basic hot reload, but those values are runtime state and are never serialized into the Scene.

---

## 6. Scene component

Add:

```cpp
struct LuaScriptComponent
{
    AssetHandle script;
    bool enabled = true;
};
```

Serialization form:

```json
"LuaScript": {
  "script": "aaaaaaaa-....",
  "enabled": true
}
```

Rules:

- `script` is a persistent AssetHandle, never a path;
- invalid/null handles are rejected when the component is enabled;
- deserialization does not execute script code;
- loading a Scene remains deterministic and side-effect free;
- script execution begins only when Application starts the ScriptEngine runtime phase.

---

## 7. Script authoring contract

A Lua script is a chunk that **returns a table** representing one script prototype/instance definition.

Example:

```lua
local PlayerController = {}

function PlayerController.OnCreate(self)
    self.speed = 120.0
end

function PlayerController.OnUpdate(self, dt)
    local x, y = self.entity:get_position()

    if Input.is_key_down("D") then
        x = x + self.speed * dt
    end

    if Input.is_key_down("A") then
        x = x - self.speed * dt
    end

    self.entity:set_position(x, y)
end

function PlayerController.OnDestroy(self)
end

return PlayerController
```

The chunk must return exactly one table. Returning another type is an explicit load error.

### Why table-per-instance

Do not use process-wide script globals as entity state.

Each entity instance must get its own table so that two entities using the same script asset can safely hold different fields such as `speed`, timers, counters, or transient state.

The implementation may execute the same source once per instance in v0.5. Compilation/prototype caching is an optimization for a later milestone unless it is simple to add without changing semantics.

---

## 8. ScriptInstance identity and ownership

`ScriptEngine` owns runtime script instances.

Conceptually:

```cpp
struct ScriptInstance
{
    UUID entityId;
    AssetHandle script;
    int tableRegistryRef;
};
```

The exact Lua registry-reference type remains private.

Instances are indexed by persistent entity UUID, not `ECS::Entity`.

Reason:

- ECS indices/generations are runtime implementation details;
- entity destruction/reconstruction can invalidate raw runtime handles;
- UUID allows every Lua call to resolve the current entity through `Scene::FindEntity` and fail safely if it no longer exists.

`lua_State*`, registry references, userdata memory, and callable function references must never be serialized.

---

## 9. Entity binding model

Each script instance receives:

```lua
self.entity
```

as Janus userdata with a private payload equivalent to:

```cpp
struct LuaEntityRef
{
    Scene* scene;
    UUID entityId;
};
```

This is a runtime capability object, not persistent Scene state.

### v0.5 Entity API

Minimum methods:

```text
entity:id() -> string
entity:name() -> string
entity:get_position() -> x, y
entity:set_position(x, y)
```

Optional if implementation remains small:

```text
entity:get_rotation()
entity:set_rotation(radians)
entity:get_scale()
entity:set_scale(x, y)
```

Every method must:

1. resolve the UUID through the current Scene;
2. verify the entity still exists;
3. verify the required component exists;
4. return a Lua error with useful context instead of dereferencing invalid state.

Never expose a raw `Scene*`, `ECS::Registry*`, `ECS::Entity`, renderer handle, native window handle, SDL type, or OpenGL type to script code.

---

## 10. Input binding

Expose a small global read-only table:

```lua
Input.is_key_down("A")
Input.was_key_pressed("Space")
Input.was_key_released("Escape")
```

The binding translates stable string names into Janus `KeyCode` values.

Unknown key names return a Lua error rather than silently returning false.

The `Input` table is backed by the `InputState` for the current Application frame. Scripts do not own or mutate input state.

No configurable input mapping system is added in v0.5; that remains v0.10 scope.

---

## 11. Lua standard-library policy

Open only the libraries needed for normal gameplay scripting.

v0.5 default:

```text
base
math
string
table
utf8
```

Do **not** expose by default:

```text
io
os
package
debug
```

Reason:

- gameplay scripts should operate through engine capabilities;
- unrestricted filesystem/process access is unnecessary for the milestone;
- a narrower VM surface will later align better with Agent permissions and project sandboxing.

This is a capability boundary, not a claim that Lua is a hostile-code security sandbox.

---

## 12. Protected-call and error model

All script load and callback execution uses protected Lua calls.

Lua errors become Janus `Result/Error` with context including when available:

```text
script AssetHandle
registered relative path
entity UUID
lifecycle callback
Lua error text / traceback
```

Example:

```text
Lua OnUpdate failed for entity 1234... (Scripts/PlayerController.lua):
.../PlayerController.lua:17: attempt to perform arithmetic on a nil value
```

No C++ exception should be used as routine script error control flow.

### Stack discipline

Every native binding/helper that manipulates the Lua stack must preserve a documented stack contract.

Use an RAII stack guard in debug/test paths to catch leaks and mismatched push/pop behavior.

---

## 13. Lifecycle semantics

### Runtime start

After Scene/Asset startup and `ApplicationClient::OnInitialize` succeed:

```text
ScriptEngine::Start
    ↓
scan enabled LuaScriptComponent entities
    ↓
load source
    ↓
create per-entity table
    ↓
inject self.entity
    ↓
OnCreate(self)
```

`OnCreate` is optional. Missing callbacks are valid.

### Per frame

Recommended frame order:

```text
Input.BeginFrame
↓
PollEvents / Input.Apply
↓
ApplicationClient::OnUpdate
↓
ScriptEngine::Update(dt, InputState)
↓
SceneRenderer::Render
↓
Present
```

This keeps scripting as gameplay/world update before rendering while preserving ApplicationClient as an outer client hook.

`OnUpdate` is optional.

### Runtime stop

Before Scene/Asset teardown:

```text
ScriptEngine::Stop
    ↓
OnDestroy(self) for live instances
    ↓
release Lua registry references
    ↓
close Lua state
```

`OnDestroy` is optional.

`ScriptEngine` must be destroyed **before Scene** so any final entity resolution remains valid during teardown.

---

## 14. Runtime reconciliation

v0.5 should tolerate Scene mutations without requiring Scene to know about ScriptEngine.

At each runtime reconciliation/update:

- enabled component + no instance -> create instance + `OnCreate`;
- component removed -> `OnDestroy` + remove instance;
- entity destroyed -> `OnDestroy` + remove instance;
- component disabled -> `OnDestroy` + remove instance;
- script AssetHandle changed -> destroy old instance, create new instance;
- unchanged live instance -> call `OnUpdate`.

A simple O(number-of-script-components) reconciliation pass is acceptable for v0.5. Do not add a general ECS system scheduler or event bus only to optimize this path.

---

## 15. Basic hot reload

Basic hot reload is file-level and development-oriented.

For each loaded Lua script asset, retain its last successful filesystem modification timestamp.

When the file timestamp changes:

```text
OnDestroy old instances using asset
↓
load/validate new source
↓
replace instances
↓
OnCreate new instances
```

v0.5 does **not** preserve arbitrary Lua table state across reload.

If the changed source fails to compile/load:

- keep the runtime error explicit;
- do not call into a half-created table;
- do not crash;
- do not silently continue with ambiguous mixed versions.

A manual `ReloadChangedScripts()` method should exist so tests can deterministically trigger reload. Application may call it once per frame or at a small polling cadence; no OS file watcher is required.

---

## 16. Application integration

Add `ScriptEngine` as an Application-owned runtime subsystem.

Conceptual ownership:

```text
Application
├── Window
├── GraphicsContext
├── Renderer2D
├── AssetRegistry
├── AssetService
├── Scene
├── ScriptEngine
└── SceneRenderer
```

Construction order must make dependencies explicit.

Teardown constraint:

```text
ScriptEngine
↓
Scene
↓
AssetService
↓
Renderer2D
↓
GraphicsContext
```

because script callbacks may still resolve Scene entities during `OnDestroy`, and AssetService owns renderer-backed resources.

The VM should not be a global singleton.

---

## 17. Runtime error semantics in Application

For disk-backed projects, script startup/update/hot-reload failures should propagate from `Application::Run()` as explicit failures, matching the v0.4 project-runtime philosophy.

For legacy no-project Application tests/clients, preserve compatibility where practical and avoid changing unrelated v0.1 behavior.

Before propagating a runtime script failure:

- call script teardown for already-created instances where safe;
- call client shutdown if client initialization completed;
- release scripting state before Scene destruction;
- keep the original script error as the returned error.

## 18. Sandbox vertical slice

Extend the committed `SandboxProject`:

```text
SandboxProject/
├── Assets/
│   └── player.png
├── Scripts/
│   └── PlayerController.lua
├── Scenes/
```

`PlayerController.lua` should move `Player` using A/D or arrow-key input.

The demonstration should prove:

```text
edit Lua
↓
run / reload
↓
entity movement changes
```

without recompiling JanusEngine.

## 19. Tests

### 19.1 Lua VM tests

- state creation/destruction;
- selected standard libraries available;
- forbidden libraries unavailable by default;
- execute valid chunk;
- syntax error -> explicit Result/Error;
- runtime error -> explicit Result/Error;
- stack top unchanged after success/failure helper calls;
- repeated VM create/destroy clean.

### 19.2 Script asset/component tests

- `lua-script` AssetType parse/stringify;
- script AssetHandle registry round-trip;
- Lua source loading through registered project-relative path;
- wrong AssetType rejection;
- missing source rejection;
- `LuaScriptComponent` Scene save/load round-trip;
- malformed/null enabled script handle rejection.

### 19.3 Script lifecycle tests

- OnCreate exactly once per instance creation;
- OnUpdate receives delta time;
- two entities using one script have isolated Lua table state;
- OnDestroy exactly once on stop;
- entity destruction reconciles and destroys instance;
- component removal/disable reconciles;
- AssetHandle replacement recreates instance;
- missing callback is valid;
- callback error includes entity/script/callback context.

### 19.4 Binding tests

- UUID entity reference resolves current entity;
- destroyed UUID fails safely;
- get/set Transform position;
- missing Transform returns script error;
- Input down/pressed/released bindings;
- invalid key name returns script error;
- no ECS/renderer/native handle leaks into Lua-facing API.

### 19.5 Hot reload tests

- changed source recreates affected instances;
- new behavior executes after reload;
- unchanged source does not recreate instances;
- syntax error on reload fails explicitly;
- no stale Lua registry refs remain after reload/stop.

### 19.6 Application E2E

From real disk fixtures:

```text
AssetRegistry
↓
Scene
↓
Lua script source
↓
LuaScriptComponent
↓
OnCreate / OnUpdate
↓
Transform mutation
↓
SceneRenderer
```

Also cover startup syntax error and runtime callback error without crash/partial teardown.

## 21. API boundary decisions

### Public

Likely public engine-facing types:

```text
LuaScriptComponent
ScriptEngine (only if a client needs explicit runtime control/testing)
```

Prefer Application to own normal ScriptEngine operation.

### Private

Keep private:

```text
lua_State
Lua registry ref integers
Lua stack helpers
LuaEntityRef implementation
native C callback functions
Lua header includes
```

Public Scene/Scripting headers must not make downstream clients depend on Lua headers.

---

## 22. Non-goals

Explicitly out of scope for v0.5:

```text
Lua coroutines / async scheduler
multi-threaded Lua execution
multiple Lua states per Scene
script bytecode packaging
state-preserving hot reload
reflection-driven automatic bindings
arbitrary component reflection
Editor script inspector
Editor play-mode isolation
CommandBus / Undo / Redo
MCP script tools
network replication
input mapping actions
prefabs
physics callbacks
animation callbacks
UI bindings
audio bindings
filesystem/process Lua APIs
third-party Lua package manager
```

These should not be pulled into a v0.5 PR merely because they are adjacent to scripting.

## 23. Acceptance criteria

v0.5 is complete only when all of the following are true:

1. Janus embeds pinned Lua 5.4.9 with Lua implementation details hidden from public consumers.
2. Scene can persist `LuaScriptComponent` using a registered Script AssetHandle.
3. A Lua script can implement optional `OnCreate`, `OnUpdate`, and `OnDestroy` callbacks.
4. Two entities using the same source receive isolated instance state.
5. Lua can safely resolve its owning entity through UUID and mutate Transform.
6. Lua can read current-frame keyboard input.
7. Script errors are protected, contextual, and propagated without crashing.
8. Basic source-file hot reload recreates affected instances without engine recompilation.
9. `SandboxProject` demonstrates Player movement authored in Lua rather than C++.
10. Script runtime tears down before Scene and leaves no live Lua refs.
11. Windows MSVC configure/build/CTest pass.
12. README documents the Lua workflow.
13. Roadmap marks v0.5 complete and v0.6 Editor Foundation as next.

The final product loop is:

```text
Persist Scene + Script AssetHandle
        ↓
Open project
        ↓
Create Lua instance
        ↓
Gameplay callback
        ↓
Read Input / mutate Entity
        ↓
Render changed Scene
        ↓
Edit Lua / basic reload
```

without recompiling JanusEngine for gameplay behavior changes.

## 24. Architectural checkpoint for v0.6

v0.5 should leave a clean seam for the Editor milestone:

- Editor can later display `LuaScriptComponent` without knowing `lua_State`;
- Play Mode can later create/destroy ScriptEngine together with RuntimeScene;
- Reflection can later describe script/component properties without replacing the VM ownership model;
- MCP can later invoke engine capabilities without directly executing arbitrary Lua internals;
- Script assets remain normal persistent AssetHandles.

The design should therefore optimize for a small, explicit runtime boundary now rather than a broad scripting framework.

# Janus v0.8 — MCP Agent Foundation Design

Date: 2026-09-05  
Status: Proposed  
Milestone: v0.8 MCP Agent Foundation  
Depends on: v0.7 Reflection + Command  
Tracking: #67, #68, #69, #70, #71, #72, #73

## 1. Stage Goal

v0.7 established the Engine capability seam required for a Human and an Agent to share one authoring model:

```text
Human Editor
    │
    ▼
EditorActions
    │
    ▼
CommandBus
    │
    ├──────────────► Scene
    │
    └──────────────► Reflection
```

The remaining product gap is that an external Agent still cannot consume that capability through a stable protocol.

v0.8 closes that gap.

The target is not "put a JSON socket around EditorActions".

The target is:

```text
                         JanusEditor
                             │
                    shared authoring state
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
         Human panels                  MCP adapter
              │                             │
         EditorActions                       │
              │                             │
              └──────────────┬──────────────┘
                             ▼
                        CommandBus
                             │
                    SceneReflection
                             │
                    ReflectionRegistry
                             │
                             ▼
                         EditorScene
```

MCP is an Engine client.

MCP must not become an alternate Scene implementation, an Editor automation hack, or a second mutation path.

The primary v0.8 acceptance statement is:

> An external MCP client can read the live Janus authoring Scene, mutate it through the same Engine commands used by Human authoring, save it, and the resulting mutation remains undoable by the Human CommandBus history.

---

## 2. Protocol Baseline

The implementation baseline is the current Model Context Protocol revision:

```text
2026-07-28
```

Janus also serves the immediately preceding compatibility era:

```text
2025-11-25
```

through stdio.

Protocol references:

- https://modelcontextprotocol.io/
- https://blog.modelcontextprotocol.io/posts/2026-07-28/
- https://modelcontextprotocol.io/specification/
- https://ts.sdk.modelcontextprotocol.io/v2/protocol-versions
- https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28

The 2026-07-28 revision is the primary semantic target.

The 2025-11-25 path exists for ecosystem compatibility, not as the architectural source of truth.

### 2.1 Why dual-era stdio

The current MCP ecosystem is transitioning between two lifecycle models:

```text
2025 era
initialize
    ↓
notifications/initialized
    ↓
session-style connection semantics
```

and:

```text
2026 era
server/discover?   optional probe
    ↓
self-describing requests
    ↓
per-request _meta
```

Janus must not ship an Agent-native milestone that only works with one narrow client generation when the compatibility cost is controlled.

v0.8 therefore supports both over one native stdio server entry.

### 2.2 Explicitly out of scope

v0.8 does not implement:

- Streamable HTTP;
- OAuth / remote authorization;
- legacy HTTP+SSE;
- Tasks extension;
- Sampling;
- Elicitation;
- Roots;
- MCP Logging protocol;
- MCP Apps;
- subscriptions/listen;
- resource subscriptions;
- runtime control;
- Agent audit;
- Transactions.

These are not required to prove the first Janus Agent authoring loop.

---

## 3. Why Native C++

Janus is a C++20 engine and v0.8 is an Engine architecture milestone.

The MCP implementation therefore remains native C++.

Do not introduce:

```text
Janus
  ↓
spawn Node/Python MCP sidecar
  ↓
IPC back into Janus
```

solely because official MCP SDKs exist for other languages.

The repository already has a pinned JSON dependency through the v0.4 persistence work.

Use the existing JSON dependency for the bounded protocol surface.

This has three benefits:

1. the protocol boundary is part of the Janus architecture rather than an external bridge;
2. lifecycle/threading/CommandBus behavior can be tested in the same C++ process;
3. Janus keeps one deployment artifact for its first native Agent path.

This does **not** mean reimplement every MCP feature.

Implement only the v0.8 protocol subset needed by the milestone.

# Part A — Module Architecture

## 4. Top-Level MCP Client Module

MCP should not live under `Engine/Core`.

Recommended repository shape:

```text
MCP/
├── CMakeLists.txt
├── Protocol/
│   ├── JsonRpc.*
│   ├── McpProtocol.*
│   └── ProtocolVersion.*
├── Transport/
│   └── StdioTransport.*
├── Registry/
│   ├── ToolRegistry.*
│   └── ResourceRegistry.*
├── Schema/
│   └── ReflectionSchemaAdapter.*
├── Resources/
│   └── SceneResources.*
├── Tools/
│   └── SceneTools.*
├── Host/
│   ├── McpHostContext.*
│   ├── McpPermissionPolicy.*
│   └── McpMainThreadDispatcher.*
└── Server/
    └── McpServer.*
```

The exact file split may remain smaller if implementation is clearer, but dependency direction must remain:

```text
MCP
 ↓
Engine public capability

Engine
 X
MCP
```

No Engine public header includes an MCP header.

---

## 5. Target Composition

The first product host is the live Editor process.

Conceptually:

```text
JanusEditor
├── ProjectSession
│   ├── EditorScene
│   ├── AssetRegistry / AssetService
│   ├── ReflectionRegistry
│   └── CommandBus
│
├── Editor panels
│   └── EditorActions
│
└── MCP server
    ├── protocol/stdio
    ├── read adapters
    └── command adapters
```

The MCP implementation does not receive an `EditorActions*`.

It receives a narrow host capability bundle.

Conceptually:

```cpp
struct McpHostContext
{
    Scene* scene;
    ReflectionRegistry* reflection;
    CommandBus* commands;
    AssetRegistry* assets;

    std::function<Result<ProjectInfo>()> queryProjectInfo;
    std::function<Result<void>()> saveCurrentScene;
    std::function<void()> markDirty;
    std::function<bool()> isAuthoringReadOnly;
};
```

This is conceptual, not a required exact API.

The important constraints are:

- MCP knows Engine capabilities;
- host-only operations are narrow callbacks/interfaces;
- MCP does not know ImGui/panels/selection/workspace layout;
- MCP does not own the authoring Scene.

---

## 6. ProjectSession Boundary

v0.7 currently makes `ProjectSession` the Human authoring document owner.

v0.8 must not make the MCP module depend on that Editor type.

Composition code may extract references from ProjectSession and populate `McpHostContext`.

Correct:

```text
Editor composition
    │
    ├── ProjectSession::GetEditorScene()
    ├── ProjectSession::GetReflectionRegistry()
    ├── ProjectSession::GetCommandBus()
    └── save/dirty callbacks
            ↓
       McpHostContext
            ↓
         MCP module
```

Incorrect:

```text
MCP module
  ↓
#include "Editor/ProjectSession.h"
  ↓
ProjectSession internals
```

This preserves the long-term architecture where a future headless authoring host can reuse MCP without bringing ImGui or Editor panels with it.

# Part B — Protocol Core

## 7. JSON-RPC 2.0 Model

v0.8 implements a small explicit JSON-RPC layer.

Required message kinds:

```text
Request
Notification
Response
Error Response
```

Required request ID forms:

- integer;
- string.

Reject unsupported/invalid shapes explicitly.

Required standard errors:

```text
-32700 Parse error
-32600 Invalid Request
-32601 Method not found
-32602 Invalid params
-32603 Internal error
```

Janus domain failures remain Janus `Result/Error` internally and are translated at the protocol boundary.

Do not throw exceptions for ordinary invalid client input.

---

## 8. Protocol Input Bounds

MCP input is untrusted process input even for local stdio.

The parser/transport must enforce finite bounds.

At minimum define limits for:

- maximum line/request bytes;
- maximum JSON nesting depth where supported by the parser;
- maximum string/tool argument size where practical;
- maximum collection count where schemas or protocol arrays can expand.

A malformed or oversized request must return/produce a controlled failure.

It must not:

- allocate without bound;
- block the Editor main thread parsing arbitrary data;
- crash the process.

Exact constants should be centralized and tested.

Do not build a general adversarial network server in v0.8; use reasonable local-process safety limits.

---

## 9. stdio Framing

The stdio transport uses newline-delimited UTF-8 JSON messages.

Rules:

```text
stdin  -> protocol input only
stdout -> protocol output only
stderr -> diagnostics allowed
```

No protocol message contains an embedded framing newline.

The serializer emits one compact JSON value followed by one newline.

### 9.1 Critical stdout rule

When MCP stdio mode is active:

> Any non-protocol write to stdout is a protocol corruption bug.

This includes:

- startup banners;
- log messages;
- debug printf;
- progress output;
- CI diagnostics.

All diagnostics must use stderr or a non-protocol sink.

Add a regression test for this.

# Part C — Protocol Era Negotiation

## 10. Supported Revisions

v0.8 supports exactly:

```text
modern: 2026-07-28
legacy: 2025-11-25
```

Do not silently claim arbitrary earlier/later versions.

Unsupported versions return an explicit protocol failure.

Version support should be represented in one central table/constant set.

---

## 11. Opening Classification

stdio has no HTTP protocol-version header.

The opening message determines the connection era.

Conceptual classifier:

```text
first meaningful message
        │
        ├── method == server/discover
        │        -> modern discovery/probe
        │
        ├── valid modern protocolVersion in _meta
        │        -> modern
        │
        ├── method == initialize
        │        -> legacy
        │
        └── claim-less legacy-shaped request
                 -> legacy compatibility policy
```

After the connection is pinned:

```text
modern connection
    X legacy initialize

legacy connection
    X modern per-request semantic switch
```

Do not allow one connection to drift between protocol eras.

---

## 12. Modern 2026-07-28 Behavior

The modern path supports:

- `server/discover`;
- self-describing request envelope validation;
- tools capability;
- resources capability;
- per-request protocol version;
- client info/capability parsing where present;
- server identity metadata on responses;
- required modern cache hints on cacheable results.

Modern requests should validate the reserved MCP envelope fields required by the current protocol behavior.

Janus does not need to consume every optional client capability in v0.8.

Unknown optional metadata may be ignored if the specification allows it.

### 12.1 server/discover

The discover result advertises at minimum:

```text
supportedVersions:
- 2026-07-28

capabilities:
- tools
- resources

server identity:
- Janus
- version/build identifier where available
```

Use conservative caching:

```json
{
  "ttlMs": 0,
  "cacheScope": "private"
}
```

unless a more stable catalog policy is intentionally proven.

---

## 13. Legacy 2025-11-25 Behavior

The compatibility path supports the normal initialization sequence:

```text
initialize
    ↓
InitializeResult
    ↓
notifications/initialized
```

Advertise only v0.8 capabilities actually supported.

Do not advertise:

- Tasks;
- Sampling;
- Elicitation;
- Prompts;
- Logging protocol;
- resource subscriptions;

unless implemented.

The legacy path then serves the same logical ToolRegistry and ResourceRegistry through the legacy wire codec.

The application behavior should be shared.

Only protocol-era serialization/lifecycle details differ.

---

## 14. One Capability Model, Two Wire Codecs

Avoid:

```text
ModernMcpTools.cpp
LegacyMcpTools.cpp
```

with duplicated business logic.

Target:

```text
             ToolRegistry / ResourceRegistry
                        │
               common handlers
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
       modern wire codec     legacy wire codec
```

The handler returns a neutral internal result.

The protocol layer converts it to the requested era.

This is particularly important for:

- structured tool output;
- cache hint fields;
- server metadata;
- initialization/discovery.

---

# Part D — Registries

## 15. ToolRegistry

Tool registration must be explicit and deterministic.

Conceptual descriptor:

```cpp
struct McpToolDescriptor
{
    std::string name;
    std::string title;
    std::string description;
    Json inputSchema;
    std::optional<Json> outputSchema;
    ToolAnnotations annotations;
    ToolHandler handler;
};
```

Requirements:

- stable name;
- duplicate rejection;
- deterministic enumeration;
- bounded handler arguments;
- schema validation before Engine mutation;
- handler returns `Result`;
- no tool stores Editor widget state.

Tool names follow MCP-compatible stable naming.

Janus v0.8 names are namespaced:

```text
scene.create_entity
scene.delete_entity
scene.rename_entity
scene.add_component
scene.remove_component
scene.set_component_property
scene.save
```

---

## 16. ResourceRegistry

Required concrete resources:

```text
engine://project/info
engine://scene/current
engine://scene/hierarchy
```

Required resource templates:

```text
engine://entity/{uuid}
engine://asset/{uuid}
```

Resource registration must be deterministic.

Do not enumerate every entity as a separate concrete static resource if the template is the better protocol model.

The registry owns URI matching/routing metadata, not Scene data.

Handlers query the injected host context at read time.

---

## 17. Cache Policy

Authoring data changes frequently.

Default modern policy for v0.8:

```text
ttlMs = 0
cacheScope = private
```

for:

- scene resources;
- entity resources;
- asset metadata if uncertain;
- catalogs unless proven immutable for the process lifetime.

This is deliberately conservative.

Janus may later introduce revision-based caching after it has explicit document/version counters.

Do not prematurely cache authoring state in the protocol layer.

# Part E — Reflection -> MCP Schema

## 18. Reflection Remains Source of Truth

v0.7 already defines:

```text
ReflectionRegistry
  ↓
ComponentDescriptor
  ↓
PropertyDescriptor
```

v0.8 consumes this.

It does not add MCP fields into Core Reflection.

Correct:

```text
Reflection Core
      │
      ▼
MCP ReflectionSchemaAdapter
      │
      ▼
JSON Schema 2020-12
```

Incorrect:

```cpp
PropertyDescriptor
{
    ...
    nlohmann::json mcpSchema;
}
```

---

## 19. Property Type Mapping

Required mapping:

| Reflection PropertyType | MCP JSON value |
| --- | --- |
| Bool | boolean |
| Int32 | integer |
| Float32 | number |
| String | string |
| Vector2 | object { x, y } |
| Color | object { r, g, b, a } |
| AssetReference | UUID string |

Use stable JSON object shapes.

Example Vector2:

```json
{
  "x": 1.0,
  "y": 2.0
}
```

Example Color:

```json
{
  "r": 1.0,
  "g": 1.0,
  "b": 1.0,
  "a": 1.0
}
```

Do not serialize C++ memory layouts.

---

## 20. AssetReference Schema

`PropertyDescriptor::referenceConstraint` already communicates intent such as:

```text
texture
lua-script
```

The MCP adapter preserves that information in the generated schema/description.

Example conceptual schema:

```json
{
  "type": "string",
  "format": "uuid",
  "description": "Asset UUID. Expected Janus asset type: texture."
}
```

Runtime validation still resolves the AssetRegistry and verifies actual AssetType.

Schema text is not a security boundary.

---

## 21. Stable Component / Property Selectors

MCP tools use stable reflected serialized names.

Example:

```json
{
  "entity": "uuid",
  "component": "Transform",
  "property": "position",
  "value": {
    "x": 4.0,
    "y": 2.0
  }
}
```

The exact serialized component case/names follow the existing Scene v1 compatibility contract.

Do not expose:

```text
ComponentTypeId numeric value
PropertyId numeric value
```

as the primary Agent API.

Those IDs remain internal stable implementation identifiers.

# Part F — Resources

## 22. engine://project/info

Purpose:

> Tell an Agent what Janus project/document it is operating on.

Minimum fields:

```text
engine
protocol support
project identity/display path
current Scene UUID
current Scene name
authoring dirty state
play/read-only state if host exposes it
```

Avoid exposing unrelated machine-local absolute paths unless explicitly required.

For project location, prefer a policy-safe normalized representation.

---

## 23. engine://scene/current

Purpose:

> Describe the active authoring Scene without dumping every entity.

Minimum fields:

```text
scene UUID
scene name
entity count
available reflected component metadata summary
authoring mode/read-only state
```

This is always the authoring Scene in v0.8.

During Play:

```text
engine://scene/current
    -> EditorScene
```

not RuntimeScene.

Runtime Agent inspection belongs to v0.9.

---

## 24. engine://scene/hierarchy

Return deterministic persistent hierarchy data.

For each entity:

```text
UUID
name
parent UUID / null
sibling order
children UUID[] or equivalent
```

Never expose:

- ECS index;
- generation;
- sparse-set positions;
- raw pointers.

---

## 25. engine://entity/{uuid}

Return one entity's authoring state.

Conceptual result:

```json
{
  "uuid": "...",
  "name": "Player",
  "parent": null,
  "components": {
    "Transform": {
      "position": { "x": 0, "y": 0 },
      "rotation": 0,
      "scale": { "x": 1, "y": 1 }
    },
    "SpriteRenderer": {
      "texture": "...",
      "size": { "x": 1, "y": 1 }
    }
  }
}
```

Only reflected authoring properties are included.

This automatically excludes:

- world transform cache;
- dirty flags if not reflected;
- TextureHandle;
- OpenGL IDs;
- Lua VM objects;
- runtime ScriptInstance state.

---

## 26. engine://asset/{uuid}

Return metadata only:

```text
AssetHandle UUID
AssetType
normalized project-relative path
```

Do not turn this resource into a generic file read endpoint.

v0.8 does not expose arbitrary filesystem bytes through MCP.

That is an intentional security and scope boundary.

# Part G — Mutation Tools

## 27. Shared Mutation Rule

Every Scene mutation tool obeys:

```text
JSON args
    ↓
protocol/schema validation
    ↓
permission check
    ↓
resolve persistent UUID / Reflection metadata
    ↓
construct existing Engine command
    ↓
shared CommandBus::Execute
    ↓
mark host document dirty
    ↓
structured result
```

There is no fallback direct mutation path.

If CommandBus execution fails:

- tool fails;
- history does not move;
- dirty state is not falsely reported as successful.

---

## 28. scene.create_entity

Input:

```text
name?
parent?      optional if v0.8 implementation supports parent creation directly
```

Output:

```text
created UUID
name
```

Use `CreateEntityCommand`.

If parent support would require a new unreviewed reparent command, keep v0.8 create as root creation instead of bypassing CommandBus.

Do not expand v0.8 solely to add a full hierarchy reparent UX/API.

---

## 29. scene.delete_entity

Input:

```text
entity UUID
```

Use existing `DeleteEntityCommand`.

Its persistent subtree snapshot semantics are exactly why MCP must reuse Engine commands.

Undo must restore:

- UUIDs;
- reflected component state;
- hierarchy;
- sibling order.

---

## 30. scene.rename_entity

Input:

```text
entity UUID
new name
```

Use existing `RenameEntityCommand`.

---

## 31. scene.add_component / remove_component

Input:

```text
entity UUID
component serialized name
```

Resolve through ReflectionRegistry.

Respect:

- required/non-removable component rules;
- duplicate component rules;
- Scene component binding constraints.

Use existing Add/Remove component commands.

---

## 32. scene.set_component_property

This is the most important v0.8 tool.

Input concept:

```text
entity UUID
component serialized name
property serialized name
typed JSON value
```

Flow:

```text
serialized names
    ↓
ReflectionRegistry
    ↓
PropertyDescriptor
    ↓
JSON -> PropertyValue
    ↓
SetPropertyCommand
```

Do not create another hard-coded switch over:

```text
Transform.position
Transform.rotation
SpriteRenderer.texture
...
```

inside MCP.

Property conversion branches only on generic `PropertyType`.

Contextual Scene semantics remain in `SceneReflection`.

Therefore:

```text
Camera.primary
```

continues to capture cross-entity mutation deltas and remains reversible.

---

## 33. scene.save

Saving is host/document behavior, not a Core Command today.

v0.8 may expose it through a narrow injected host capability:

```text
MCP scene.save
    ↓
McpHostContext::SaveCurrentScene()
    ↓
existing atomic SceneSerializer path
```

Requirements:

- save current authoring Scene only;
- use existing project Scene destination;
- no arbitrary output path argument;
- successful save clears dirty according to host semantics;
- failed save leaves dirty state correct;
- return explicit failure.

Do not add generic filesystem write tools.

# Part H — Tool Schemas and Results

## 34. JSON Schema 2020-12

Tool `inputSchema` / `outputSchema` follow JSON Schema 2020-12 semantics.

Use:

```json
{
  "type": "object",
  "additionalProperties": false
}
```

where practical for argument objects.

Schemas must be deterministic.

Avoid including transient Scene state such as "currently existing entity UUID enum" in `tools/list`, because that makes the catalog unstable and large.

Entity IDs are validated at call time.

---

## 35. Reflection-Driven SetProperty Schema

There are two acceptable implementation levels.

### Preferred

Generate a deterministic `oneOf` over reflected component/property branches so the client sees typed values.

Conceptually:

```text
oneOf
├── Transform.position -> Vector2
├── Transform.rotation -> number
├── Transform.scale -> Vector2
├── SpriteRenderer.texture -> UUID string
└── ...
```

### Acceptable fallback

Use stable component/property enums plus a broad JSON `value`, but validate it immediately against Reflection metadata and provide strong descriptions.

The preferred form has substantially higher Agent usability and should be attempted if it remains maintainable.

Do not compromise Reflection/Command boundaries solely for prettier JSON Schema.

---

## 36. Tool Results

Successful mutation tools should return structured JSON.

Keep v0.8 outputs object-shaped even on the modern protocol so legacy structured-content compatibility stays simple.

Example:

```json
{
  "ok": true,
  "entity": "..."
}
```

Where structured content is emitted, also emit a text JSON fallback when required/recommended by compatibility behavior.

Do not return private C++ error strings containing arbitrary implementation addresses or raw stack memory.

# Part I — Threading and Live Editor Integration

## 37. Why a Thread Boundary Is Required

A live Editor UI loop cannot block indefinitely on:

```text
std::getline(stdin)
```

and protocol input must not mutate Scene from an arbitrary reader thread.

Therefore protocol I/O and Engine mutation are separated.

Recommended model:

```text
        MCP client process
               │
               ▼
             stdin
               │
        stdio reader thread
               │
       parse protocol envelope
               │
               ▼
        PendingRequestQueue
               │
               ▼
         Editor main thread
               │
       McpMainThreadDispatcher
               │
        ┌──────┴──────┐
        ▼             ▼
   resource read   CommandBus
        │             │
        └──────┬──────┘
               ▼
           response
               │
        ResponseQueue
               │
        stdio writer
               │
               ▼
             stdout
```

A dedicated writer thread or serialized writer path is acceptable.

The invariant matters more than the exact number of threads.

---

## 38. Main-Thread Ownership Rule

The following authoring state is main-thread owned:

- EditorScene;
- CommandBus;
- Reflection-backed Scene mutation;
- ProjectSession dirty/save state;
- Editor-facing Asset/Scene state where current implementation assumes main-thread ownership.

Protocol I/O threads must not call these directly.

They may:

- parse JSON;
- validate protocol-level shapes;
- enqueue a request;
- serialize a completed neutral response.

---

## 39. No Engine Lock While Blocking on I/O

Never:

```text
lock Scene
   ↓
write stdout / wait client
```

or:

```text
lock CommandBus
   ↓
read stdin
```

The main thread handles one bounded request operation and produces an owned response value.

The protocol layer then performs blocking I/O without holding Engine state.

---

## 40. Request Completion Model

A request crossing the main-thread boundary needs explicit completion ownership.

Acceptable designs include:

- request object + promise/future;
- request ID + response queue;
- condition-variable completion with deterministic shutdown.

Do not use detached threads.

Do not allow a pending request to reference stack memory owned by the reader loop after enqueue.

Shutdown must either:

- finish queued requests;
- or fail/cancel them deterministically.

---

## 41. Frame Pump Budget

MCP is not allowed to freeze the Editor by draining an unbounded request queue in one frame.

The dispatcher should apply a bounded policy, for example:

- maximum N requests per frame;
- or maximum MCP dispatch time budget per frame.

Exact tuning may be simple in v0.8.

The key requirement is deterministic fairness with the UI/runtime loop.

---

# Part J — Editor Hosting

## 42. Launch Mode

Provide an explicit launch mode, conceptually:

```powershell
JanusEditor --project SandboxProject --mcp-stdio
```

Exact argument parsing can follow existing conventions.

In this mode:

- Editor UI still runs;
- stdio MCP server is active;
- stdout is reserved;
- Agent mutations operate on the same EditorScene shown to the user.

A normal Editor launch without `--mcp-stdio` must preserve existing behavior.

---

## 43. Human / Agent Shared History

This is the core v0.8 product proof.

Example:

```text
Human creates Player
    ↓
history: [Create Player]

Agent moves Player
    ↓
history: [Create Player][Set Transform.position]

Human clicks Undo
    ↓
Agent move is reversed
```

There is one CommandBus history.

Do not create:

```text
HumanHistory
AgentHistory
```

in v0.8.

---

## 44. Play Mode Semantics

v0.7 already makes authoring read-only during Play.

MCP follows the same policy.

During Play:

```text
read resources
    -> allowed, describe EditorScene

write tools
    -> rejected by authoring read-only policy

runtime Scene access
    -> not exposed in v0.8
```

Do not special-case MCP to mutate EditorScene while Human UI is locked.

That would violate shared semantics.

---

## 45. Dirty State

Successful Agent authoring mutations change persisted authoring state.

Therefore successful MCP:

- create;
- delete;
- rename;
- add/remove component;
- set property;

must integrate with the same host dirty semantics as Human authoring.

Failed commands do not mark dirty.

`scene.save` clears dirty only on successful persistence.

---

# Part K — Permission Foundation

## 46. Purpose

stdio is local, but "local" is not equivalent to "unrestricted".

v0.8 adds a small explicit permission seam so future transports do not need to retrofit authorization into every handler.

Suggested operation classes:

```text
ProjectRead
SceneRead
SceneWrite
SceneSave
```

Conceptual API:

```cpp
Result<void> Authorize(
    McpOperation operation,
    const McpRequestContext& request) const;
```

The policy is injected/owned by the host.

MCP registries do not contain hard-coded "all requests trusted forever" logic.

---

## 47. v0.8 Local Policy

The default local Editor stdio mode may allow all currently exposed v0.8 operations.

The value of the permission foundation is:

- explicit classification;
- one enforcement point;
- tests for deny behavior;
- no accidental future tool bypass.

It does not require an interactive confirmation dialog in v0.8.

MCP clients may provide their own Human confirmation UX based on tool metadata.

---

## 48. Explicitly Forbidden Capability Surface

v0.8 does not expose generic tools for:

- execute process/shell;
- arbitrary file read;
- arbitrary file write;
- arbitrary network request;
- DLL/plugin loading;
- memory read/write;
- C++ pointer access.

Janus MCP is a structured Engine capability API.

It is not a generic remote shell.

# Part L — Error Mapping

## 49. Protocol vs Tool Errors

Separate:

### Protocol errors

Malformed JSON-RPC/MCP requests:

```text
Parse error
Invalid Request
Method not found
Invalid params
Unsupported protocol version
```

These use JSON-RPC/MCP error responses.

### Tool execution errors

A valid `tools/call` may fail because:

- entity missing;
- component missing;
- wrong PropertyValue type;
- component removal forbidden;
- AssetReference wrong type;
- authoring read-only during Play;
- permission denied;
- Scene save failed.

These are valid MCP tool call failures and should be represented according to tool-result error semantics rather than pretending the JSON-RPC request itself was malformed.

Keep the distinction explicit in tests.

---

## 50. Error Context

Expose useful stable context:

```text
entity UUID
component/property name
operation
high-level cause
```

Do not expose:

- raw pointers;
- internal container addresses;
- secret filesystem content;
- implementation stack dumps.

# Part P — Known Boundaries After v0.8

## 61. No Runtime Agent Loop Yet

After v0.8 an Agent can:

```text
read authoring project
read Scene
modify Scene
save Scene
```

It cannot yet:

```text
runtime.play
runtime.pause
runtime.stop
runtime.step
read runtime entity state
read profiler
reason from structured runtime logs
transaction rollback
```

Those are v0.9.

This distinction must remain visible in README.

---

## 62. No Transaction Yet

One Agent request maps to one Engine command for current mutation tools.

A future multi-command Agent operation may create multiple history entries.

Do not invent a v0.8 transaction layer to hide this.

v0.9 owns:

```text
Transaction Begin
Commit
Rollback
Audit / Agent Activity
```

---

## 63. No User-Facing Reparent Tool

The existing hierarchy can be read.

Delete undo can restore hierarchy.

A generic Agent reparent mutation is intentionally not part of the first tool list unless the Engine already has a safe reusable command before implementation reaches #71.

Do not bypass CommandBus by calling `Scene::SetParent` directly from MCP.

If reparent becomes necessary, add the Engine command first and update the design intentionally.

# Part Q — Risks

## 64. Risk: MCP Becomes Editor Automation

Failure mode:

```text
MCP tool
  ↓
EditorActions
  ↓
ImGui/selection assumptions
```

Mitigation:

- MCP consumes Engine Reflection + Commands;
- ProjectSession is only composition source;
- no Editor includes in MCP target.

---

## 65. Risk: Protocol Thread Corrupts ECS/Scene

Failure mode:

```text
stdin worker
  ↓
CommandBus::Execute
```

while Editor main thread renders/edits the same Scene.

Mitigation:

- explicit main-thread dispatcher;
- no direct Engine authoring references used from protocol I/O thread;
- thread-boundary tests.

---

## 66. Risk: stdout Logs Break Every MCP Client

This is a high-probability stdio integration failure.

Mitigation:

- protocol-only stdout invariant;
- stderr diagnostics;
- test raw child-process stdout frames;
- audit existing startup/log paths in MCP mode.

---

## 67. Risk: Reflection Schema Diverges from Command Validation

Mitigation:

- schema derives from the same PropertyDescriptor;
- call-time conversion still resolves Reflection metadata;
- schema never replaces Engine validation.

---

## 68. Risk: Dual Protocol Era Doubles Business Logic

Mitigation:

- one registry;
- one resource handler;
- one tool handler;
- two thin lifecycle/wire codecs only.

---

## 69. Risk: Tool Catalog Changes Every Frame

If tool schemas enumerate current entities/assets dynamically, clients lose cache stability and prompts churn.

Mitigation:

- static capability-oriented tools;
- entity/asset IDs supplied as arguments;
- dynamic state exposed as Resources;
- deterministic schema generation from Reflection component metadata.

---

## 70. Risk: Agent Can Escape Project Through Asset Paths

Mitigation:

- Asset MCP resource exposes registry metadata only;
- paths remain normalized/project-relative;
- no arbitrary path argument;
- no generic file read/write tool.

---

## 71. Risk: v0.8 Pulls v0.9 Forward

Mitigation:

Reject scope expansion into:

- runtime control;
- Profiler;
- log streaming;
- Transactions;
- Audit;
- Tasks;
- remote transport.

The deliverable is the first safe authoring MCP seam.

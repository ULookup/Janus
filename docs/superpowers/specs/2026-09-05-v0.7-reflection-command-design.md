# Janus v0.7 — Reflection + Command Design

Date: 2026-09-05  
Status: Implemented  
Milestone: v0.7 Reflection + Command  
Depends on: v0.6 Editor Foundation  
Tracking: #50, #51, #52, #53, #54, #55, #56, #57

Implementation note: the design was delivered through the staged v0.7 PR chain and closed with the #57 end-to-end regression/documentation pass. v0.8 consumes the Engine Reflection + Command seam without depending on EditorActions.

## 1. Stage Goal

v0.6 established a usable Human authoring loop:

```text
JanusEditor
    ↓
ProjectSession
    ↓
EditorScene
    ├── Hierarchy
    ├── Inspector
    ├── Asset Browser
    ├── Scene View
    └── Save
            ↓
        Play / Stop
            ↓
       RuntimeScene
```

However, the v0.6 authoring implementation is intentionally transitional:

- Inspector knows each built-in component explicitly.
- SceneSerializer and SceneDeserializer repeat the built-in property schema manually.
- EditorActions centralizes mutation, but still mutates Scene/component state directly.
- There is no generic metadata model for future MCP schemas.
- There is no command history, Undo, or Redo.

v0.7 replaces that temporary seam with the first reusable Engine Capability layer:

```text
                     Human Editor
                         │
                         ▼
                    EditorActions
                         │
                         ▼
                     CommandBus
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
         Reflection              Scene
              │                     │
      Component Metadata        ECS runtime
      Property Metadata
```

The primary v0.7 acceptance statement is:

> A Human edits a reflected property in Inspector, Janus executes a SetPropertyCommand, and the operation can be undone and redone without Editor owning a parallel implementation.

The v0.8 consequence is equally important:

```text
Editor ───────────────┐
                      │
                      ▼
                Reflection + Command
                      ▲
                      │
MCP (v0.8) ───────────┘
```

MCP must later consume the same metadata and command mechanism. v0.7 therefore must not place these capabilities inside Editor.

v0.7 includes:

## 3. Explicit Non-Goals

v0.7 does **not** introduce:

- MCP protocol or transport
- JSON-RPC
- permission system
- transactions
- audit / Agent Activity
- runtime Agent control
- profiler
- prefab
- animation
- physics
- audio
- game UI
- docking persistence
- custom user-defined C++ component hot registration
- plugin ABI
- generic binary serialization
- arbitrary Lua table reflection

These remain later milestones.

The v0.7 design should be sufficient for v0.8 MCP without implementing v0.8 early.

## 4. Current Baseline

Current `main` already provides the required migration seams:

### Scene authoring identity

Entities have persistent UUIDs through `EntityIdentityComponent`.

```text
Persistent Entity UUID
        ≠
ECS index + generation
```

Commands must use the persistent UUID.

### EditorActions

v0.6 already routes panel mutation through:

- CreateEntity
- DeleteEntity
- RenameEntity
- SetTransform
- Add/Remove SpriteRenderer
- Set SpriteRenderer / texture
- Add/Remove Camera
- Set Camera
- Add/Remove LuaScript
- Set LuaScript enabled / asset

This means panels do not need a complete rewrite. EditorActions is the migration adapter.

### Manual Inspector

The current Inspector explicitly knows:

- Transform
- SpriteRenderer
- Camera
- LuaScript

### Manual Scene serialization

The current Scene v1 JSON schema explicitly writes and parses the same component fields.

v0.7 must remove this duplicated property knowledge while keeping the disk schema compatible.

# Part A — Reflection

## 5. Reflection Ownership

Reflection must be explicitly owned.

Do not introduce:

```cpp
ReflectionRegistry::Get();
GlobalReflectionManager;
static mutable registry;
```

Preferred model:

```text
Application / host
      │
      └── owns ReflectionRegistry
              │
              ├── built-in component registration
              ├── Inspector query
              ├── Scene serialization query
              └── Command property access
```

The registry object can be shared by reference with clients that need metadata.

The ownership location may evolve, but the API must not require global mutable state.

---

## 6. Reflection Layer Boundary

Reflection belongs to Engine public capability.

Conceptually:

```text
Engine/
└── Core/
    └── Reflection/
        ├── PropertyType
        ├── PropertyValue
        ├── PropertyDescriptor
        ├── ComponentDescriptor
        └── ReflectionRegistry
```

Built-in Scene component registration may live closer to Scene:

```text
Engine/
└── Scene/
    └── SceneReflection.*
```

This keeps Core Reflection independent from Scene while allowing Scene to register its own types.

Core Reflection must not depend on:

- Scene
- ECS
- Asset
- Renderer
- Editor
- ImGui
- MCP
- nlohmann/json
- OpenGL
- Lua C API

This boundary also applies to PropertyValue. Core Reflection therefore uses neutral authoring value wrappers rather than importing higher-level Asset/Renderer types.

---

## 7. Stable Metadata Identity

Runtime RTTI names are not a persistence or protocol contract.

Do not use compiler-specific:

```cpp
typeid(T).name()
```

as the stable serialized identity.

Each reflected component has a canonical stable name, for example:

```text
Transform
SpriteRenderer
Camera
LuaScript
```

Each property has a canonical stable name within the component:

```text
Transform.position
Transform.rotation
Transform.scale
```

An internal typed/hash ID may be derived from the canonical name, but:

- collisions must be detectable during registration;
- stable strings remain available for Scene JSON and future MCP schema;
- registration order must not determine identity.

---

## 8. PropertyValue

v0.7 needs a finite authoring value model, not arbitrary C++ object reflection.

Conceptually:

```cpp
struct ColorValue
{
    f32 r = 1.0f;
    f32 g = 1.0f;
    f32 b = 1.0f;
    f32 a = 1.0f;
};

struct AssetReferenceValue
{
    UUID id;
};

enum class PropertyType
{
    Bool,
    Int32,
    Float32,
    String,
    Vector2,
    Color,
    AssetReference
};

using PropertyValue = std::variant<
    bool,
    i32,
    f32,
    std::string,
    Vector2,
    ColorValue,
    AssetReferenceValue>;
```

This set is intentionally small and sufficient for current built-in authoring state.

`ColorValue` is a Core-neutral value and is converted by Scene registration code to/from the current Renderer `Color` field.

`AssetReferenceValue` contains only a UUID. Scene registration code converts it to/from `AssetHandle`, while higher-level authoring validation applies the expected asset kind (for example Texture or LuaScript). Core Reflection therefore does not depend on the Asset module.

Do not add values solely because a runtime field exists.

Examples that do **not** belong in PropertyValue during v0.7:

- ECS::Entity
- TextureHandle
- RenderTargetHandle
- raw pointer
- lua_State*
- Mat4 world transform cache

---

## 9. Accessors, Not Raw Memory Offsets

Property metadata must support safe typed access.

Avoid requiring all properties to be represented as:

```text
base pointer + byte offset
```

because component fields may require domain conversion (for example AssetHandle <-> AssetReferenceValue or Renderer Color <-> ColorValue) and future components may need validation/accessor logic.

Conceptual descriptor:

```cpp
struct PropertyDescriptor
{
    PropertyId id;
    std::string name;
    std::string serializedName;
    PropertyType type;

    bool visible = true;
    bool editable = true;
    bool serializable = true;

    Result<PropertyValue> Get(const void* component) const;
    Result<void> Set(void* component, const PropertyValue& value) const;
};
```

The concrete implementation can use templated registration helpers internally, but consumers use the non-template descriptor interface.

The descriptor setter is a low-level typed field restore/access primitive. It must not enforce Human editability itself. This distinction is required because a property may be `editable = false` but still `serializable = true` and therefore must be restorable during deserialization or command snapshot restore.

Policy is layered as:

```text
PropertyDescriptor::Set
    ↓
low-level typed local restore

Scene authoring capability
    ↓
checks editable + contextual invariants
    ↓
ApplyPropertyMutation
```

A property that is editable or serializable requires a registered setter in v0.7.

---

## 10. ComponentDescriptor

A reflected component needs more than a list of properties.

Conceptually:

```cpp
struct ComponentDescriptor
{
    ComponentTypeId id;
    std::string name;
    std::string serializedName;

    bool removable;
    bool serializable;

    std::vector<PropertyDescriptor> properties;

    // Scene-specific binding is provided outside Core Reflection
    // or through registered opaque component access callbacks.
};
```

The final implementation must support later generic capability operations:

```text
Has Component
Add Component
Remove Component
Get Property
Set Property
```

without Editor or MCP compiling a switch over every component type.

## 11. Built-in Reflected Authoring State

### Transform

Persistent / reflected:

| Property | Type | Visible | Editable | Serializable |
|---|---|---:|---:|---:|
| position | Vector2 | yes | yes | yes |
| rotation | Float32 | yes | yes | yes |
| scale | Vector2 | yes | yes | yes |

Not reflected:

- worldPosition
- worldRotationRadians
- worldScale
- dirty

Transform is required and non-removable.

### SpriteRenderer

Persistent / reflected:

| Property | Type | Visible | Editable | Serializable |
|---|---|---:|---:|---:|
| texture | AssetReference(Texture) | yes | yes | yes |
| size | Vector2 | yes | yes | yes |
| color | Color | yes | yes | yes |
| layer | Int32 | yes | yes | yes |
| uvMin | Vector2 | optional UI visibility | yes | yes |
| uvMax | Vector2 | optional UI visibility | yes | yes |
| enabled | Bool | yes | yes | yes |

SpriteRenderer is optional/removable.

### Camera

| Property | Type | Visible | Editable | Serializable |
|---|---|---:|---:|---:|
| zoom | Float32 | yes | yes | yes |
| primary | Bool | yes | yes | yes |

Camera is optional/removable.

### LuaScript

| Property | Type | Visible | Editable | Serializable |
|---|---|---:|---:|---:|
| script | AssetReference(LuaScript) | yes | yes | yes |
| enabled | Bool | yes | yes | yes |

LuaScript is optional/removable.

### EntityIdentity and Hierarchy

Entity UUID and hierarchy links are structural Scene data, not ordinary removable Inspector components in v0.7.

Entity name remains a first-class entity operation and is handled by RenameEntityCommand.

Do not expose Entity UUID as an editable property.

## 12. Generic Scene Property Capability

Reflection metadata alone does not own ECS storage.

Janus needs a generic Scene-facing bridge.

The external behavior should be equivalent to:

```text
Entity UUID
    +
ComponentTypeId
    +
PropertyId
        ↓
resolve runtime Entity
        ↓
resolve reflected component accessor
        ↓
Get / Set PropertyValue
```

Required operations:

```text
HasComponent(entityUUID, componentType)
AddComponent(entityUUID, componentType)
RemoveComponent(entityUUID, componentType)

GetProperty(entityUUID, componentType, property)
SetProperty(entityUUID, componentType, property, value)
```

Consumers must not obtain mutable ECS internal storage as part of this API.

---

## 13. Validation

Reflection does not mean bypassing invariants.

Validation exists at two levels.

### Property-level

Examples:

- Camera.zoom must remain within valid engine semantics.
- PropertyValue type must match PropertyType.

### Component/context-level

Examples:

- enabled LuaScript requires a valid script handle.
- texture property may require an AssetReference that resolves to Texture metadata.
- script property may require an AssetReference that resolves to LuaScript metadata.

Asset type validation requires project AssetRegistry context and therefore must not turn Core Reflection into an AssetService owner.

The authoring capability/command layer should perform contextual validation before committing a mutation.

On a multi-field invariant, failed validation must restore the old value before returning failure.

### Contextual Scene mutation

A PropertyDescriptor getter/setter is a **local field adapter**. It must not secretly mutate unrelated entities.

Some authoring properties have Scene-level semantics. The current example is `Camera.primary`: setting one Camera primary currently clears the primary flag on other Cameras.

Therefore the Scene-facing authoring capability must wrap local reflection access with an explicit contextual mutation operation.

Conceptually:

```cpp
struct PropertyChange
{
    UUID entity;
    ComponentTypeId component;
    PropertyId property;
    PropertyValue before;
    PropertyValue after;
};

struct PropertyMutationDelta
{
    std::vector<PropertyChange> changes;
};

Result<PropertyMutationDelta> ApplyPropertyMutation(...);
Result<void> RestorePropertyMutation(...);
```

For a normal property, the delta contains one change.

For a contextual property such as `Camera.primary = true`, the delta may contain multiple affected entities:

```text
OldPrimary.Camera.primary: true  -> false
Target.Camera.primary:     false -> true
```

This keeps cross-entity policy outside Core Reflection while giving Command Undo/Redo an exact reversible state.

Contextual validation such as AssetRegistry type checks or LuaScript invariants also belongs at this Scene/authoring capability boundary.

# Part B — Serialization Integration

## 14. Compatibility Rule

v0.7 does not change the current Scene file contract merely to adopt Reflection internally.

Current files must remain loadable:

```text
schema = janus.scene
version = 1
```

Do not bump version solely because the implementation becomes metadata-driven.

`SandboxProject/Scenes/Battle.scene` must continue to work.

### v1 compatibility policy

Scene schema version 1 remains strict:

- an unknown serialized component name is an error;
- an unknown serialized property name is an error;
- a reflected serializable property required by a present component must exist;
- invalid PropertyValue shape/type is an error.

Janus must not silently drop unknown authoring data and then overwrite the Scene on a later Save.

If future versions need additive/tolerant migration semantics, that change must be explicit and versioned rather than inferred from Reflection.

---

## 15. Structural Data Remains Explicit

These Scene fields stay explicitly owned by Scene serialization:

```text
scene.id
scene.name

entity.id
entity.name
entity.parent
entity.siblingOrder
```

Reflection is used for the `components` object.

This is intentional.

Hierarchy is a graph reconstruction problem, not a normal flat editable property bag.

---

## 16. Reflection Registry Ownership in Persistence

Persistence must use an explicitly-owned registry. Do not hide a singleton and do not create a new built-in registry inside every Serialize/Deserialize call.

The v0.7 ownership model is:

```text
Managed Runtime Application
    └── ReflectionRegistry

Editor ProjectSession
    └── ReflectionRegistry
          ├── Scene load/save
          ├── Scene clone / RuntimeSession
          ├── Inspector
          └── CommandBus
```

Each host registers built-in Scene metadata once for its lifetime.

Scene persistence and cloning therefore receive the active registry explicitly, conceptually:

```text
SceneSerializer(scene, reflection)
SceneDeserializer(text, reflection)
SceneCloner(scene, reflection)
```

The Editor RuntimeSession uses the same ProjectSession registry when cloning EditorScene. Future MCP obtains the same Engine capability rather than constructing its own metadata universe.

---

## 17. Reflection-Driven Component Serialization

Target flow:

```text
Scene Entity
    ↓
ReflectionRegistry
    ↓
enumerate serializable component descriptors
    ↓
component exists?
    ↓ yes
enumerate serializable properties
    ↓
PropertyValue
    ↓
Scene JSON codec
```

JSON conversion belongs in Scene serialization, not Core Reflection.

```text
PropertyValue
    ↓
SceneSerializer PropertyValueJson(...)
```

and:

```text
JSON
    ↓
SceneDeserializer ParsePropertyValue(...)
    ↓
PropertyValue
    ↓
reflected setter
```

This prevents nlohmann/json from becoming a dependency of the Reflection core.

---

## 18. Preserve Serialized Names

The current Scene JSON spelling is part of the compatibility contract.

Examples:

```text
Transform.rotation
SpriteRenderer.uvMin
LuaScript.script
```

Reflection metadata therefore supports a stable serialized name.

The C++ field name does not need to equal the serialized property name.

For example:

```text
C++: rotationRadians
JSON: rotation
```

---

## 19. Deserialization Semantics

The existing safe two-phase model remains:

```text
Parse + validate root
    ↓
Create all entities with UUIDs
    ↓
Restore reflected components/properties
    ↓
Resolve parent UUID references
    ↓
Validate hierarchy
    ↓
Expose complete Scene
```

A failed reflected property restore must fail the whole Deserialize result.

Do not return a partially initialized Scene.

# Part C — Command Architecture

## 20. Command Core Boundary

CommandBus is reusable Engine infrastructure.

Conceptually:

```text
Engine/
└── Core/
    └── Command/
        ├── ICommand
        └── CommandBus
```

Scene authoring commands can live near Scene:

```text
Engine/
└── Scene/
    └── Command/
        ├── SetPropertyCommand
        ├── AddComponentCommand
        ├── RemoveComponentCommand
        ├── CreateEntityCommand
        ├── DeleteEntityCommand
        └── RenameEntityCommand
```

Core Command must not know Editor, MCP, ImGui, or Scene internals.

---

## 21. ICommand Contract

A command must have explicit reversible semantics.

Conceptually:

```cpp
class ICommand
{
public:
    virtual ~ICommand() = default;

    virtual Result<void> Execute() = 0;
    virtual Result<void> Undo() = 0;
    virtual Result<void> Redo() = 0;

    virtual std::string_view Describe() const noexcept = 0;
};
```

A command may hold references to required Engine capability objects whose lifetime is guaranteed by the owning authoring session.

It must not store ECS index/generation as persistent identity.

Entity commands store UUIDs.

---

## 22. CommandBus History Model

Recommended model:

```text
history:
[ C0 ][ C1 ][ C2 ][ C3 ]
                  ^
                cursor
```

Semantics:

### Execute new command

1. validate/execute command;
2. if execution fails, history is unchanged;
3. if cursor is not at the end, discard redo tail;
4. append command;
5. move cursor to end.

### Undo

1. if no undo candidate, return unavailable/no-op policy;
2. call command Undo;
3. if Undo fails, cursor does not move;
4. on success move cursor backward.

### Redo

1. call command Redo;
2. if Redo fails, cursor does not move;
3. on success move cursor forward.

The implementation can choose an index/cursor representation, but these externally visible semantics are required.

---

## 23. History Lifetime

Commands may reference an active Scene and persistent UUIDs.

Therefore command history is scoped to one active authoring document/session.

History must be cleared when:

- opening another project;
- replacing/reloading the authoring Scene as a new document state;
- destroying the current authoring session.

Play/Stop does **not** replace EditorScene and therefore should not inherently destroy authoring history.

RuntimeScene never enters the authoring CommandBus.

---

## 24. SetPropertyCommand

State:

```text
target entity UUID
component type ID
property ID
requested PropertyValue
captured PropertyMutationDelta?
```

First Execute:

1. resolve UUID/component/property;
2. ask the Scene authoring capability to apply the contextual property mutation;
3. capture the returned PropertyMutationDelta exactly once;
4. enter history only after the mutation succeeds.

Undo:

```text
restore every PropertyChange.before value
```

Redo:

```text
restore every PropertyChange.after value
```

Redo must replay the captured delta instead of rediscovering side effects against a potentially different Scene state.

For ordinary properties the delta contains one entry, so this remains equivalent to classic old/new value capture.

For `Camera.primary`, the delta also captures other Cameras whose primary state changes. Undo therefore restores the previous primary Camera correctly.

The command must not recapture a different mutation delta during Redo.

---

## 25. AddComponentCommand

Execute:

- resolve entity UUID;
- reject required/existing invalid operation;
- add default reflected component.

Undo:

- remove that component.

Redo:

- add it again.

If future components need non-default initialization, the command can carry an initial reflected snapshot. v0.7 built-ins do not require a generic constructor-argument system.

---

## 26. RemoveComponentCommand

Remove is destructive and must snapshot authoring state before deletion.

State:

```text
entity UUID
component type ID
ComponentSnapshot
```

ComponentSnapshot contains serializable reflected property values.

Execute:

1. resolve component;
2. snapshot properties;
3. remove.

Undo:

1. add component;
2. restore snapshot through reflected setters.

Redo:

- remove again without replacing the original snapshot.

Transform removal is rejected because Transform is required.

---

## 27. CreateEntityCommand

The command owns a predetermined persistent UUID.

First Execute:

```text
CreateEntityWithUUID(commandUUID, name)
```

Undo:

```text
Destroy entity commandUUID
```

Redo:

```text
CreateEntityWithUUID(same commandUUID, name)
```

The ECS runtime index may differ. That is expected.

This explicitly validates the persistent identity design.

---

## 28. DeleteEntityCommand

Delete is the most important destructive Undo case.

Do not snapshot ECS handles.

Before deletion, capture a recursive persistent subtree snapshot.

Conceptually:

```text
EntitySubtreeSnapshot
└── EntityRecord[]
    ├── UUID
    ├── name
    ├── parent UUID / external parent UUID
    ├── sibling order
    └── ComponentSnapshot[]
        ├── component type
        └── reflected property values
```

Execute:

1. resolve root UUID;
2. capture complete subtree snapshot;
3. delete root recursively.

Undo:

1. recreate all entities using original UUIDs;
2. restore reflected components/properties;
3. restore internal hierarchy;
4. reconnect root to original external parent if it still exists;
5. restore deterministic sibling order.

Redo:

- delete the same UUID root again.

If UUID restoration collides with an existing entity, Undo fails explicitly instead of silently generating new identities.

---

## 29. RenameEntityCommand

Entity name is structural authoring state and not modeled as a removable component property in v0.7.

Rename command state:

```text
entity UUID
old name
new name
```

Execute captures old name once.

Undo/Redo restore old/new name.

---

## 30. Reparent Boundary

Generic Reparent is part of the long-term Command architecture, but a full user-facing Reparent workflow is not required to close v0.7 unless implementation needs a reusable primitive for DeleteEntity snapshot restoration.

If a ReparentEntityCommand is introduced during v0.7:

- it must use UUIDs;
- reject cycles;
- capture previous parent and sibling order;
- restore exact authoring hierarchy on Undo.

Do not expand v0.7 into drag/drop hierarchy UX solely because the command primitive exists.

---

# Part D — Editor Migration

## 31. EditorActions Remains the Editor Adapter

Do not make ImGui panels construct Scene commands directly everywhere.

Keep:

```text
Panel
  ↓
EditorActions
  ↓
CommandBus
  ↓
Engine
```

EditorActions provides ergonomic UI operations and contextual validation.

Its implementation changes from direct mutation to command construction/execution.

Example:

```text
v0.6
Inspector
  ↓
EditorActions::SetTransform
  ↓
transform.position = ...

v0.7
Inspector
  ↓
EditorActions::SetProperty
  ↓
SetPropertyCommand
  ↓
CommandBus
  ↓
Reflection property setter
```

Specialized compatibility helpers may remain temporarily if they delegate to the generic path.

---

## 32. Generic Inspector

Inspector no longer contains one block per built-in component.

Target:

```text
selected entity UUID
    ↓
ReflectionRegistry components
    ↓
component exists on entity?
    ↓
for each visible PropertyDescriptor
    ↓
PropertyType
    ├── Bool       -> Checkbox
    ├── Int32      -> integer widget
    ├── Float32    -> float widget
    ├── String     -> text input
    ├── Vector2    -> DragFloat2
    ├── Color      -> ColorEdit
    └── AssetReference -> typed asset reference UI
```

Inspector is an Editor adapter over metadata.

It must not become the owner of Reflection rules.

---

## 33. Asset Reference UI Metadata

An AssetReference property may optionally declare the expected asset kind.

Examples:

```text
SpriteRenderer.texture -> Texture
LuaScript.script       -> LuaScript
```

This allows:

- typed Asset Browser assignment in v0.7;
- future generic MCP validation/schema in v0.8.

Do not encode this rule by checking component names in Inspector.

---

## 34. Play Mode

Existing authoring isolation remains.

During Play:

```text
EditorScene        RuntimeScene
    │                   │
 read-only UI         Lua updates
```

Editor authoring commands are rejected/disabled while Play Mode is active according to the existing v0.6 policy.

Undo/Redo must not mutate RuntimeScene.

---

## 35. Dirty State

A successful authoring mutation changes the persisted document state.

Successful:

- Execute
- Undo
- Redo

must mark the Editor Scene dirty.

Command Core itself should not depend on ProjectSession.

Dirty-state integration belongs at the authoring host/Editor adapter boundary.

Failed commands do not mark dirty.

---

## 36. Undo / Redo UI

v0.7 requires a minimal Human-facing affordance.

At minimum:

```text
Undo
Redo
```

with disabled state when unavailable.

Keyboard shortcuts are useful but not required to define the Engine architecture.

Do not introduce a second Editor-only history stack.

---

v0.8 should be able to build schemas from Reflection:

```text
ReflectionRegistry
    ↓
ComponentDescriptor
    ↓
PropertyDescriptor
    ↓
MCP JSON Schema adapter
```

Reflection Core itself does not construct MCP JSON.

## 38. Future MCP Write Path

Future tools:

```text
scene.create_entity
scene.delete_entity
scene.add_component
scene.remove_component
scene.set_component_property
```

must map to the same command classes used by Editor.

Target:

```text
Editor ─────┐
            │
            ▼
        CommandBus
            ▲
            │
MCP ────────┘
```

MCP must not depend on EditorActions.

EditorActions is the Human UI adapter; Reflection + Command are Engine capability.

---

## 39. No Transaction Yet

v0.9 plans Transaction/Audit.

v0.7 history should not prematurely implement:

- BeginTransaction
- Commit
- Rollback groups
- Agent Activity log
- permissions

However, command objects and history should remain composable enough that a later transaction can own/execute a group of commands.

# Part F — Error and Consistency Rules

## 40. Result/Error

All recoverable Reflection and Command failures use Janus Result/Error.

Examples:

- unknown component
- unknown property
- wrong PropertyValue type
- stale/missing UUID
- forbidden component removal
- duplicate UUID on undo
- invalid asset type
- invalid component invariant
- failed undo restore

Do not use exceptions as routine command flow.

---

## 41. Atomicity of Individual Commands

A single command must not leave partial state when its own operation fails.

Examples:

### SetProperty

If post-set component validation fails:

```text
restore old value
return failure
```

### RemoveComponent Undo

If restoration cannot complete:

- report explicit failure;
- avoid claiming Undo succeeded;
- history cursor does not move.

### DeleteEntity Undo

Validate reconstructability before destructive restore work where practical.

Where complete prevalidation is impossible, restoration helpers must clean up partial recreated state before returning failure.

# Part I — Risks

## 48. Risk: Reflection Becomes an Unsafe C++ Runtime Type System

Mitigation:

- reflect only current authoring value types;
- use typed accessors;
- no arbitrary pointer casting in consumers;
- do not attempt full language reflection.

---

## 49. Risk: Reflection Breaks Stable Scene Files

Mitigation:

- preserve canonical serialized names;
- keep Scene structure explicit;
- keep schema version 1;
- run existing fixtures through new path before removing manual code.

---

## 50. Risk: CommandBus Becomes Editor Infrastructure

Mitigation:

- Command classes live in Engine;
- EditorActions is only an adapter;
- future MCP directly consumes Engine Reflection + Command.

---

## 51. Risk: Delete Undo Uses Runtime ECS Identity

Mitigation:

- snapshot persistent UUIDs and reflected state only;
- recreate through CreateEntityWithUUID;
- rebuild hierarchy from UUID relationships.

---

## 52. Risk: Undo Failure Corrupts History

Mitigation:

- cursor moves only after successful Undo/Redo;
- destructive restore validates first where practical;
- partial restoration must be cleaned up on failure.

---

## 53. Risk: v0.7 Pulls v0.8/v0.9 Forward

Mitigation:

Do not add MCP JSON-RPC, permissions, transactions, audit, or profiler.

The v0.7 deliverable is the reusable capability seam, not the Agent protocol.

# 54. Acceptance Criteria

v0.7 is complete only when all of the following hold.

### Reflection

- current built-in authoring components have explicit stable metadata;
- runtime-only state is not reflected;
- generic property access works by persistent entity identity + metadata;
- no global reflection singleton exists.

### Serialization

- Scene v1 disk format remains compatible;
- reflected metadata is the property source of truth;
- existing SandboxProject loads successfully;
- no runtime/GPU state appears in Scene files.

### Command

- property/component/entity mutations execute through CommandBus;
- Undo and Redo are deterministic;
- destructive operations restore persistent UUID/component/hierarchy state;
- failed operations do not lie about history state.

### Editor

- Inspector is metadata-driven for current built-ins;
- EditorActions no longer directly performs migrated component mutations;
- moving Player through Inspector produces a SetPropertyCommand;
- user can Undo and Redo the move;
- Play Mode authoring isolation remains correct.

### Architecture

- Editor and future MCP can share Reflection + Command without MCP depending on Editor;
- no v0.8 protocol or v0.9 transaction/audit work is pulled forward.

### Verification

- relevant unit/integration tests pass;
- full `windows-msvc-debug-tests` configure/build/CTest passes;
- documentation is updated;
- roadmap marks v0.7 complete only after the full vertical slice is demonstrated.

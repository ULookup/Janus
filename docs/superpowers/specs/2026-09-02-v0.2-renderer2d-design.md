# Janus v0.2 Renderer2D Design

## 1. Background and Goal

Janus v0.1 has established the Engine Foundation: Application lifecycle, SDL3 window, OpenGL 4.5 Core Context, frame time, events, keyboard input, file system, logging, and tests. The current milestone is v0.2 Renderer2D.

The goal of v0.2 is to build a complete CPU-to-GPU 2D rendering pipeline while keeping OpenGL and SDL types behind Engine boundaries. Sandbox must be able to render multiple textured and transparent sprites, move an orthographic camera, and produce reproducible 1K/10K sprite benchmark data.

This document defines the design that the implementation plan will follow.

## 2. Scope

In scope:

- Public `Renderer2D` immediate-mode API.
- Public renderer value types: `Sprite`, `OrthographicCamera`, `Color`, `Viewport`, `TextureRegion`, `Vector2`, `RendererStatistics`.
- Internal `RenderDevice` abstraction.
- Internal GPU resources: vertex buffer, index buffer, vertex array, shader, texture, framebuffer.
- `RenderQueue` for deterministic sprite sorting.
- `BatchRenderer` for sprite batching.
- `RendererStatistics` for frame-level renderer metrics.
- OpenGL 4.5 Core backend using glad.
- Application ownership of `Renderer2D`.
- Sandbox demo with procedural textures, moving camera, alpha blending, and atlas UV regions.
- Separate benchmark target for 1K/10K sprites.

Out of scope:

- ECS, Scene, Hierarchy, or TransformComponent.
- Asset system, texture file import, or stb_image.
- Material system.
- Editor, MCP, or Agent renderer control.
- 3D rendering, Vulkan, or render graph.
- Dynamic texture atlas packing algorithms.

## 3. Key Decisions

1. Public API is high-level only. `Renderer2D` is public; `RenderDevice` and OpenGL backend are private Engine implementation.
2. Use `glad v2.0.8` as the OpenGL loader. It is confined to `Engine/Backend/OpenGL`.
3. Use `glm 1.0.3` for internal math. Public APIs expose Janus-owned value types, not `glm` types.
4. Framebuffers are fully supported internally but are not public API.
5. Batch key uses `layer + texture/atlas + blend mode`. Sprite UV regions support atlas rendering.
6. Application owns `Renderer2D` and automatically synchronizes the viewport before client update.
7. Testing is GPU-free for automated tests; OpenGL rendering is verified manually through Sandbox and Benchmark.
8. `Renderer2D` uses immediate mode. `SubmitSprite` is `void`; `EndFrame` returns `Result<void>`.
9. Renderer sorting uses layer and stable submission order. Alpha blending is the only v0.2 blend mode.
10. The 2D world uses Y-up coordinates and a center-origin default camera.
11. Sprites use world units, default center pivot, and rotate around that center.
12. Shader is a single built-in 2D sprite shader and is not public API.

## 4. Architecture

```text
Sandbox / future Scene / future Editor
                 |
                 v
         Engine Public API
                 |
                 v
          Renderer2D
           |       |
           v       v
     RenderQueue  BatchRenderer
           |       |
           +---+---+
               v
         RenderDevice
               |
               v
       OpenGLRenderDevice
               |
               v
        glad / OpenGL 4.5
```

`Renderer2D` is the only rendering entry point exposed to clients in v0.2. It orchestrates queueing, batching, and statistics. `RenderDevice` is an internal abstraction so Renderer logic can be tested without a GPU and so the OpenGL backend remains replaceable.

## 5. Public API Design

### 5.1 Vector2

```cpp
namespace Janus
{
struct Vector2
{
    f32 x = 0.0f;
    f32 y = 0.0f;
};
}
```

### 5.2 Color

```cpp
namespace Janus
{
struct Color
{
    f32 r = 1.0f;
    f32 g = 1.0f;
    f32 b = 1.0f;
    f32 a = 1.0f;

    static constexpr Color White();
};
}
```

### 5.3 Viewport

```cpp
namespace Janus
{
struct Viewport
{
    u32 width = 0;
    u32 height = 0;
};
}
```

### 5.4 TextureRegion

```cpp
namespace Janus
{
struct TextureRegion
{
    Vector2 min;
    Vector2 max;

    static constexpr TextureRegion Full();
};
}
```

`TextureRegion` uses normalized UV coordinates. `Full()` returns `[0,0]` to `[1,1]`.

### 5.5 OrthographicCamera

```cpp
namespace Janus
{
struct OrthographicCamera
{
    Vector2 position;
    f32 rotationRadians = 0.0f;
    f32 zoom = 1.0f;
};
}
```

The view-projection matrix is computed internally from the camera and viewport. Clients do not manipulate matrices directly.

### 5.6 Sprite

```cpp
namespace Janus
{
struct Sprite
{
    TextureHandle texture;
    Vector2 position;
    Vector2 size;
    f32 rotationRadians = 0.0f;
    Color color = Color::White();
    i32 layer = 0;
    TextureRegion uv = TextureRegion::Full();
};
}
```

`TextureHandle` is an opaque handle returned by the renderer when the client creates or obtains a texture. In v0.2 the public handle remains opaque; clients receive it from the renderer factory or demo helper, not from OpenGL.

### 5.7 RendererStatistics

```cpp
namespace Janus
{
struct RendererStatistics
{
    u32 spriteCount = 0;
    u32 batchCount = 0;
    u32 drawCallCount = 0;
    u32 textureBindCount = 0;
    u32 vertexCount = 0;
    u32 indexCount = 0;

    void Reset();
};
}
```

### 5.8 Renderer2D

```cpp
namespace Janus
{
class Renderer2D
{
public:
    [[nodiscard]] static Result<std::unique_ptr<Renderer2D>> Create();

    void BeginFrame(
        const OrthographicCamera& camera,
        Viewport viewport);

    void SubmitSprite(const Sprite& sprite);

    [[nodiscard]] Result<void> EndFrame();

    [[nodiscard]] const RendererStatistics& GetStatistics() const noexcept;

    [[nodiscard]] Result<TextureHandle> CreateTexture(
        const TextureDesc& desc);

    void DestroyTexture(TextureHandle handle);
};
}
```

`Create()` constructs the default OpenGL-backed renderer. The constructor that accepts a `RenderDevice&` is test-only or internal and is not part of the stable public client path.

## 6. Internal Design

### 6.1 RenderDevice

`RenderDevice` is the internal abstraction for GPU resources and draw submission. It uses Janus-owned handles and never exposes GL types.

Responsibilities:

- Create and destroy vertex buffers.
- Create and destroy index buffers.
- Create and destroy vertex arrays.
- Create and destroy shaders.
- Create and destroy textures.
- Create and destroy framebuffers.
- Set viewport.
- Clear the current target.
- Submit indexed draw commands.

All creation and validation failures return `Result<T>`.

### 6.2 RenderQueue

`RenderQueue` owns the per-frame submission list and sorting logic. It does not know about GPU resources.

Responsibilities:

- Clear submissions at the start of a frame.
- Accept a `Sprite`.
- Sort sprites deterministically.
- Produce batches grouped by `layer`, `texture`, and `blendMode`.

### 6.3 BatchRenderer

`BatchRenderer` owns transient vertex and index data for the current frame.

Responsibilities:

- Consume sorted batches.
- Generate a quad per sprite: four vertices and six indices.
- Write position, UV, and color attributes.
- Build GPU buffers through `RenderDevice`.
- Emit `DrawCommand`s and update `RendererStatistics`.

### 6.4 OpenGL backend

Files under `Engine/Backend/OpenGL` are private implementation and may include glad and OpenGL types.

Responsibilities:

- Load OpenGL 4.5 Core functions with glad.
- Implement `RenderDevice` using OpenGL objects.
- Compile and link the built-in sprite shader.
- Upload textures and configure filter/wrap parameters.
- Create and validate framebuffers.
- Destroy resources deterministically.

Public headers must not include `glad/gl.h`, `GLuint`, `GLenum`, or call `gl*`.

## 7. Data Flow

Each frame:

1. Application polls events and updates input.
2. Application synchronizes the current window size into `Renderer2D`.
3. Client calls `Renderer2D::BeginFrame(camera, viewport)`.
4. Client calls `Renderer2D::SubmitSprite` zero or more times.
5. Client calls `Renderer2D::EndFrame`.
6. `EndFrame` clears the render target, sorts submitted sprites, batches them, builds GPU resources, and issues draw calls.
7. Application presents the graphics context.

The camera view-projection matrix is computed once per frame from the camera and viewport.

## 8. Error Handling

- `Renderer2D::Create` returns `Result`.
- `EndFrame` returns `Result` and reports GPU resource, shader, or draw submission failures.
- `SubmitSprite` does not return `Result`; it is a hot-path queue operation.
- Invalid texture handles are asserted in Debug and skipped in Release.
- OpenGL shader compilation and linking failures include the OpenGL info log in the returned error message.
- Texture creation validates dimensions and format before uploading.
- Framebuffer creation validates attachment completeness.
- Resource destruction is deterministic and must not throw.

## 9. Lifetime and Ownership

Ownership:

```text
Application
  owns Window
  owns GraphicsContext
  owns Renderer2D
```

Destruction order:

1. `Renderer2D` and its GPU resources are destroyed.
2. `GraphicsContext` is destroyed.
3. `Window` is destroyed.
4. Platform is shut down.

`Renderer2D` owns its `RenderDevice` backend. Texture handles created through `Renderer2D::CreateTexture` are owned by the renderer resource table until explicitly destroyed.

## 10. Testing and Verification

Automated tests:

- Orthographic camera math.
- RenderQueue sorting and stable ordering.
- Batch key grouping by layer, texture, and blend mode.
- BatchRenderer vertex/index generation.
- RendererStatistics accumulation.
- `Renderer2D` Begin/Submit/End behavior using a fake `RenderDevice`.

Automated tests must not require a real window, display, or GPU.

Manual verification:

- Sandbox renders multiple procedural textures.
- Sandbox renders transparent sprites with correct alpha blending.
- Sandbox moves the orthographic camera.
- Benchmark runs 1K and 10K sprites and records:
  - Frame Time
  - Draw Calls
  - Batch Count
  - Sprite Count

Source audit:

```powershell
rg -n "GLuint|GLenum|gl[A-Z]" Engine Sandbox Benchmarks -g "*.h" -g "*.cpp"
```

OpenGL identifiers must appear only under `Engine/Backend/OpenGL`.

## 11. Dependencies

Add:

| Dependency | Version | Role | Boundary |
| --- | --- | --- | --- |
| glad | v2.0.8 | OpenGL 4.5 Core function loading | `Engine/Backend/OpenGL` only |
| glm | 1.0.3 | vector/matrix math | Internal renderer/math implementation; not exposed in public API |

Do not add stb_image, texture atlas packers, or other asset-loading dependencies in v0.2.

## 13. Acceptance Criteria

- Sandbox renders multiple textures and transparent sprites.
- Sandbox demonstrates moving camera and atlas UV regions.
- 1K and 10K benchmark data is recorded.
- Public API contains no SDL, `GLuint`, `GLenum`, or `gl*` identifiers.
- OpenGL backend is private.
- Automated tests cover camera math, queue ordering, batching, statistics, and `Renderer2D` orchestration.
- Both normal and test presets configure/build successfully.
- `ctest --preset windows-msvc-debug-tests` reports zero failures.
- Benchmark preset builds and runs manually.
- `git diff --check` reports no whitespace errors.

## 14. Risks

- OpenGL backend may be difficult to unit test in CI. Mitigation: keep it thin and isolate all testable logic behind `RenderDevice`.
- Batch implementation may become complicated. Mitigation: keep v0.2 batching limited to per-texture quads and avoid dynamic atlas packing.
- Public API may drift. Mitigation: freeze the v0.2 public surface in this spec and keep `RenderDevice` internal.
- Dependency integration may fail on Windows/MSVC. Mitigation: pin glad and glm versions, add them through `FetchContent`, and verify with the repository presets.

## 1. 交付目标

v0.9 交付一条能够重复验证的 Agent 开发闭环：

```text
读取作者态 → 通过 Command 修改 → 启动隔离 Runtime
    → 暂停/单步 → 读取 Runtime 与日志 → 判断结果
    → 停止 → 修正作者态 → 再次验证
```

完整版本还必须提供共享 Profiler、可撤销事务和 Agent Activity。先交付上述最小闭环，再补齐剩余能力；中间阶段完成不等于 v0.9 完成。

不按版本序号换算总体完成百分比，不提前宣称完整 PRD MVP 或 v1.0 成立。创建项目等 Human MVP 需求仍需独立验收。

## 2. 范围与依据

范围来自《版本路线图》v0.9：

| 必须交付 | v0.9 的最小完整定义 |
|---|---|
| Runtime Control | Play、Pause、Resume（通过 Play）、Stop、单帧 Step |
| Runtime Resources | 当前运行状态、指定 UUID 的运行态组件值 |
| Structured Logs | 有界、可筛选、有游标的日志；Editor/MCP 共用 |
| Profiler | CPU Scope、Renderer Statistics、Editor 面板、MCP Resource |
| Transaction | Begin、Commit、Rollback、命令分组、失败和断连处理 |
| Audit | Agent 修改与控制操作的结果、关联命令、事务、Human Undo 可追踪 |
| Validation | Engine 测试、Host 集成、真实 stdio 子进程 E2E、真实 Editor 冒烟 |

明确不包含：HTTP/OAuth、远程多用户协作、MCP Tasks、任意 shell、Agent Build/Test Runner、生产 Headless、Physics/Audio/Animation/Game UI、Lua 任意 table 反射、Runtime 写属性、Play 修改 Apply、Reparent/Duplicate、资产导入事务、磁盘事务、GPU Profiler、通用 Job System。

文档口径需要明确：

- PRD 的完整 Runtime P0 与路线图的 Game Systems P1 存在优先级口径差异。本方案按路线图划定 v0.9，不把 v0.10 提前。
- 技术架构的 `Validate All → Execute` 是批处理概念图，不能直接作为多请求事务的完整算法。本方案采用逐命令校验、临时执行和逆序补偿，见第 9 节；不声称支持数据库隔离或不可失败的回滚。
- PRD 的 Agent Testing、完整 Headless 和 Dry Run 不因 v0.9 名称包含“验证”而自动进入本版本。

## 3. 当前实现与必要改造

| 当前代码事实 | v0.9 改造 |
|---|---|
| `Editor/RuntimeSession` 持有 Scene Clone 和 ScriptEngine，只有 `m_Running` | 把通用运行会话迁入 Engine，增加明确状态、运行实例 ID、帧号和时间 |
| `ProjectSession::IsPlaying()` 同时服务更新和作者态写保护 | 分离“存在 Runtime”与“正在连续更新”，避免 Pause 后解除写保护 |
| Editor 遇到 Update 错误立即 Stop 并丢弃 Runtime | 改为保留故障现场，停止推进，显式 Stop 后销毁 |
| MCP 在 OnUpdate 开头 Pump，I/O worker 等待主线程结果 | 保留模型；单步在主线程同步完成后才返回，不能返回排队成功冒充执行完成 |
| SceneTools 与 EditorActions 分别调用 CommandBus 并标 dirty | 在 ProjectSession 统一作者态执行入口，双方通过同一入口完成 guard/dirty/history |
| EditorConsole 只有本地 Info/Error 消息 | 接入 Engine 中的有界结构化 LogStore，保留必要兼容包装 |
| Renderer2D 每次 BeginFrame 重置统计 | 每个 Scene/Game render pass 完成后立即复制统计，不能只读最后一次计数 |
| CommandBus 只有 Execute/Undo/Redo，最多 256 条历史 | 增加命令分组与事务状态；保留失败时 cursor 不移动的契约 |
| 外部测试宿主只 Pump，不更新 Runtime | 接入生产的 Runtime tick 能力和测试时钟，不复制 gameplay 或 MCP handlers |

以上是拟修改的 API/架构范围。本次只新增设计文档；这些能力尚未写入实现。

## 4. 所有权和模块边界

```text
Application / Editor host
├── DiagnosticSession
│   ├── LogStore
│   └── 与现有日志系统连接的 RAII 注册对象
├── ProjectSession
│   ├── EditorScene / ReflectionRegistry / AssetRegistry
│   ├── CommandBus（包含作者态事务和历史）
│   ├── RuntimeSession?（Engine 类型）
│   ├── CpuProfiler / 完成帧历史
│   └── CommandBus 内置 Activity 存储（项目会话级、有界）
└── McpEditorHost
    ├── 协议和 stdio worker
    └── Dispatcher → Permission → 注入的能力 → Registry handlers
```

模块落点：

- `Engine/Runtime/`：RuntimeSession、RuntimeState/Status、运行实例和时间模型。依赖 Scene/Scripting/Core，不能依赖 Editor/MCP/ImGui；不是 Core 的子模块。
- `Engine/Core/Log/`：结构化日志值、查询和线程安全存储；不包含 MCP JSON 或 Editor 类型。
- `Engine/Core/Profiling/`：显式 recorder、RAII scope、CPU trace 值；不导入 Renderer。
- `Engine/Diagnostics/`：组合 CPU frame 与 RendererStatistics 的不可变诊断快照、Activity 数据。跨模块组合放这里，不能倒置 Core 依赖。
- `Engine/Core/Command/`：CommandGroup、事务状态、执行来源、命令 ID/事件；仍然不认识 Scene、Editor 或 MCP。
- `MCP/Tools/`、`MCP/Resources/`：typed capability 到 JSON 的适配；通过注入函数获取动态 Runtime，不能缓存启动时的 RuntimeScene 指针。
- `Editor/`：组合上述 Engine 能力、UI 和生命周期。ProjectSession 协调作者态/运行态互斥；MCP 不调用 EditorActions。

不新增依赖，继续使用现有 C++20、spdlog、nlohmann/json、Catch2 和 Python E2E。新 target 沿用 warnings 和 PRIVATE `.cpp` 规则。

迁移 RuntimeSession 时保留必要的短期 Editor wrapper/alias，随后更新调用方；不同时重写 ManagedRuntime Application。其既有 Lua、清理顺序和 Sandbox 测试必须保持通过，公共日志/Profiler 可通过可选注入消费。

销毁顺序：先停止接收 MCP 请求并唤醒等待者，再在主线程处理未完成事务，停止 Runtime/ScriptEngine，清空引用 Scene 的历史，最后释放 Scene、metadata 和资源。日志 sink 先解除注册再销毁存储；shutdown 中不得等待自己所属的线程。

## 5. Runtime 状态机

### 5.1 状态与计数

`RuntimeState = Stopped | Playing | Paused | Faulted`。Stopped 表示无运行会话，其余状态都持有隔离 RuntimeScene。

拟提供：`HasRuntime()`、`GetRuntimeState()`、`GetRuntimeStatus()`。旧 `IsPlaying()` 如暂时保留，应维持“运行模式已启动”的兼容意义并标明迁移方向；禁止再把它同时用作 tick 判据和写保护。

| 操作 | Stopped | Playing | Paused | Faulted |
|---|---|---|---|---|
| Play | Clone、OnCreate，进入 Playing 或初始 Paused | 成功，返回已有状态 | Resume 同一运行实例 | 拒绝，要求先 Stop |
| Pause | InvalidState | 切换 Paused | 成功，无副作用 | InvalidState |
| Step | InvalidState | InvalidState，要求先 Pause | 恰好推进一次后保持 Paused | InvalidState |
| Stop | 成功，无副作用 | OnDestroy、销毁 | OnDestroy、销毁 | 清理并销毁，错误需返回 |

Play 从 Stopped 接受可选 `startPaused`（默认 false）；Paused 调用 Play 不再次 Clone、不重复 OnCreate。对已有会话不得用 `startPaused` 隐式改变行为：显式提供此参数时拒绝，避免重试歧义。普通无参数 Play 在 Playing 是幂等读取状态，在 Paused 是 Resume。

状态中包含：

- `runtimeId`：每次成功启动生成的新 UUID；Stop 后当前值为 null，保留最近一次终止摘要；
- `frameIndex`：成功完成的 simulation update 次数，起始为 0；OnCreate 不计为 simulation frame；
- `simulationTimeSeconds`：成功完成的 timestep 之和；
- `lastStepSeconds`、`entityCount`、`scriptInstanceCount`；
- `lastError`、`failedFrameIndex`：错误码、受限长度消息和相关上下文；
- `authoringReadOnly`：表示常规、无事务凭证的作者态入口是否只读；HasRuntime 或事务锁/故障隔离时为 true。事务 owner 的带凭证子命令是明确例外，由独立 guard 校验，不能仅凭该布尔值决定所有写入。

启动失败必须清理部分构造对象，仍为 Stopped，并在日志/终止摘要中保留原因。Update/Reload 失败转 Faulted，保留 RuntimeScene 供读取。故障帧可能已部分执行，不能把它算作成功帧；资源必须返回 `partialUpdate=true` 和失败帧号。v0.9 不承诺每帧运行逻辑回滚或单脚本故障隔离。

Stop 即使 OnDestroy 返回错误也应完成可完成的清理并进入 Stopped；返回失败结果中同时携带最终状态，避免 Agent 误认为 Runtime 仍在运行。

### 5.2 时间、输入与热重载

- 连续运行沿用 host 提供并限制过的 timestep；不改变现有普通 Gameplay 时间语义。
- Step 固定使用 `1/60 s`，每次请求只执行一帧；不接受无限帧循环、任意 dt 或异步 task。
- Step 在主线程调用与连续运行相同的 simulation update 路径。完成后的响应已经能用于下一次资源查询，但不保证 GPU 呈现已经完成。
- Paused 的普通 Editor frame 不执行 Lua OnUpdate，也不推进 simulation 时间；Scene/Game View 仍可渲染。
- 正常运行沿用当前输入；MCP Step 使用独立的全零 InputState，由 RuntimeSession 在本次 update 前复制到自己持有的输入缓冲。ScriptEngine 的引用绑定该长寿命缓冲，不能绑定临时对象。v0.9 不提供 Agent 输入注入。
- 暂停时不自动热重载；Step 也不隐式热重载。Playing/Resume 后在下一次正常 tick 的安全点执行既有 reload 检查。改变脚本后的确定性验收使用 Stop → Play，明确初始化版本。
- 固定 timestep 和空输入只保证本次 step 的推进语义，不承诺随机数、外部文件或任意 Lua 程序全局确定性。

主线程调用是协作式的：现有 Lua 若出现无限循环，单帧 Step、事务到期检查或 MCP 请求仍可能无法及时返回。v0.9 不通过不安全的强制线程终止宣称有硬实时超时；Lua instruction watchdog 属于后续独立工作，不将“每次只推进一帧”误写成“任意脚本都有固定执行时限”。

主线程顺序固定为：输入采样 → MCP Pump/事务到期处理 → Human 控制操作 → 如状态仍为 Playing 则正常 tick → 视图渲染 → 发布完整诊断帧。Step 完成后保持 Paused，因此同一 host frame 不会再自动推进一帧。

### 5.3 Runtime Resources

保留现有 `engine://scene/*` 和 `engine://entity/{uuid}` 的作者态含义，不在 Play 时偷偷切换数据源。

新增：

- `engine://runtime/status`；
- `engine://runtime/entity/{uuid}`。

实体读取返回 `runtimeId`、`frameIndex`、`state`、`partialUpdate`、entity UUID/name 和通过现有 Reflection 读取的当前组件值。这里读的是 RuntimeScene 的实际字段，不是 EditorScene 的副本值。

只暴露已注册的组件属性；不增加 GPU handle、ECS index/generation、Transform cache 或 Lua table 任意字段。不同请求可能跨帧，Agent 必须比较运行实例/帧号；需要稳定对比时先 Pause。不存在 Runtime、UUID 不存在、实例已结束都返回明确错误，不回退读取 EditorScene。

读取在主线程完成并复制为值快照，不返回跨线程 Scene 指针，不更新 Transform cache、不触发 reload、不推进 Runtime。

## 6. 统一结构化日志

日志记录至少包含：`sequence`、UTC timestamp、level、category、message、可选 projectSessionId/runtimeId/frameIndex/entity UUID/errorCode/correlationId。

- 新增有界 LogStore，默认 2,000 条，单条消息最多 8 KiB；限制是 host 配置，不能让 Agent 任意扩容。
- sequence 在诊断会话内单调增加；查询/清空不复用序号。记录被淘汰时返回 `oldestSequence`、`nextCursor`、`droppedCount` 和 gap 标记。
- `engine://logs/recent` 返回默认最近 100 条；支持 URI query 的 `after`、`limit`（1–200）、`level`、`category`、`runtimeId`。游标前进基于已扫描的原始序号，避免筛选无匹配时重复扫描同一段。
- 默认无 after 时取最新窗口，并按 sequence 升序返回；带 after 时向前扫描并分页。非法数字、重复参数、未知参数显式拒绝。
- 页数限制之外还有编码后字节预算，必须低于现有 1 MiB 协议帧上限并预留 envelope 空间。容量不足只返回可容纳前缀，nextCursor 不能越过尚未返回的匹配记录；极端单条记录无法容纳时返回显式摘要与 truncation，不能使游标永远卡在同一记录。
- 现有 spdlog logger 通过附加 sink 写入同一 LogStore，保留 stderr 输出。新增分类入口为 Runtime/Lua/Asset/Renderer/Editor/MCP 标注 category；旧消息可保留 Core/Sandbox 分类，不用字符串猜测来源。
- EditorConsole 改为该存储的视图，Info/Warning/Error 筛选与 MCP 共用查询。已有 PushInfo/PushError 包装写入统一存储，避免双份错误。
- Lua 编译/运行错误记录原始错误与 traceback 摘要；RuntimeSession 是运行失败的主记录点，Editor 不再次记同一条错误。可用 correlationId 去重。
- 日志写入允许多线程，锁只保护短时间 append/snapshot；格式化和 JSON 序列化在锁外。sink 不得调用自己的 logger 递归记录。

日志保留期仅限进程会话，无磁盘持久化要求。读取日志不会为该读取再生成日志，避免观测接口自激增。Agent 无 Clear 日志工具；Human Clear 只影响存储窗口并保留游标连续性。

## 7. Profiler：先保证数据可信

### 7.1 数据和采集

Core 提供显式 `CpuProfiler` 和 RAII `CpuScope`。宏必须接收 recorder/context，不引入全局 Profiler singleton。限定 owner 线程，使用帧内索引表示 scope/parent，记录起始偏移、duration 和 name。

CPU capture 默认开启，scope 使用单调时钟；记录器支持关闭采样。测试注入时钟，不断言机器绝对速度。存储默认保留 120 个完成的 host frames、每帧最多 4,096 个 scopes，超限截断并报告丢弃数；scope name 来源于固定代码位置，限制长度。

首批 scope：HostFrame、McpPump、RuntimeUpdate、LuaUpdate、ScriptReload、SceneRender、GameRender、EditorUI。Runtime Update 的专用采样还标注 runtimeId/frameIndex；MCP Step 可产生 simulation sample，但不能冒充一个已完成的 GPU frame。

跨线程 scope 使用每线程缓冲或短锁提交，不在持有 Scene/CommandBus 相关状态时等待 profiler。发布时只收集已关闭 scopes；跨 frame scope 记录起始 frame 和完成 frame，不能伪造完整父子树。v0.9 首批性能插桩以主线程为主，多线程安全由合成测试验证。

### 7.2 统计口径

```text
FrameProfileSnapshot
├── hostFrameId / timestamp / runtimeId / simulationFrameIndex
├── wallFrameSeconds / cpuWorkSeconds / runtimeUpdateSeconds / luaSeconds
├── scopes / droppedScopes / complete
└── renderPasses[]
    ├── SceneView: RendererStatistics 或 unavailable
    └── GameView: RendererStatistics 或 unavailable
```

- CPU inclusive duration 不能直接求和当作总耗时；面板明确使用 inclusive 或 exclusive 口径。
- 每个 render pass 结束立即复制 Renderer2D::GetStatistics，防止后续 clear/default framebuffer pass 覆盖。
- 分开显示 SceneView、GameView；总 DrawCall 可求和，但 SpriteCount 总和表示提交次数，不表示去重后的世界实体数。
- 未渲染的视图标记 unavailable，不能沿用上一帧当本帧数据；Physics/Animation 尚未实现，不填虚假 0ms 计时。
- CPU Render Time 是 CPU 提交时间，不是 GPU 时间。Present/VSync 等等待若未被采集，明确说明 wallFrame 与 CPU 工作时间的差异。

新增 `engine://profiler/latest-frame`，读取最后一个完成的快照；尚无样本返回 `available=false`，不触发采样。可通过同一资源的 `frameId` 参数读取有界历史；已淘汰返回明确 unavailable/gap，不无限等待。Editor Profiler 使用同一份 Engine snapshot。

本版本不增加异步 capture task、GPU timer query、火焰图编辑器或自动瓶颈诊断算法。Agent 可基于准确数据推理。

## 8. 作者态执行入口与命令事件

ProjectSession 新增统一的 ExecuteAuthoring/UndoAuthoring/RedoAuthoring 入口（命名实现时遵循现有风格），处理 Runtime/transaction guard、CommandBus、dirty 和 selection 的后处理。EditorActions 负责构造命令/适配 UI；SceneTools 通过注入的执行回调提交同样的 Engine Scene commands。

`McpSceneToolContext` 不再把可写 CommandBus 当作绕过 guard 的默认路径；改为 typed execute 回调。MCP 不依赖 EditorActions 或 ImGui。宿主注入是状态协调，不能在 Host 重写组件 mutation。

Core Command 定义不依赖协议的 `CommandExecutionContext`：来源 Human/Agent/System、host 生成的 connection/session identity、可选 transactionId/correlationId。Engine typed IDs 在 JSON 边界编码为字符串，避免 JSON 数字精度问题。

执行生成命令 receipt/event：commandId、操作 Execute/Undo/Redo、结果、Describe、可选 effect metadata。Scene commands 提供 UUID、组件/属性 canonical names 与受限 before/after 摘要，Camera.primary 包括跨实体 effect；Delete 的完整重建快照仍由命令私有持有，Audit 不复制整棵树。

事件只在结果确定后发出。observer 不能在回调中重入 CommandBus，也不能通过日志/审计失败回滚已经成功的业务修改；用 dropped/error 计数报告诊断缺失。事务内 receipt 标明 Pending，不能显示为 Committed。

## 9. Transaction：会话级、独占写、可见临时状态

### 9.1 选择和限制

采用 live reversible transaction：每个子命令仍作用于同一 EditorScene，但先保留在 pending group，Commit 时作为一条历史记录接管，不能再次执行。

选择原因：复用已有 Scene command/snapshot，支持“创建 UUID → 添加组件 → 设置属性”的依赖链，不新增 Shadow Scene、文件系统事务或并发版本合并。

边界：一次只允许一个作者态事务、仅 Stopped、无嵌套、只包含六类现有 Scene mutation。Save、Runtime Control、Undo/Redo、日志/Profiler 操作不能成为事务子命令。事务提供命令级补偿，不提供读隔离：Human 和 Agent 可以看到临时场景，资源和 Editor 必须明确标记 transactionActive/provisional。

### 9.2 生命周期和协议

新增 Tools：`transaction.begin`、`transaction.commit`、`transaction.rollback`；新增 `engine://transaction/status`。Begin 接受 label（最多 128 字符），返回不透明 transactionId。

活跃事务期间：

- owner 的 Scene mutation 必须携带匹配的 transactionId；这作为工具参数的可选字段扩展，不能隐式把任意连接写操作归入事务；
- 没有 token、错误 owner/token 的写入拒绝，不能加入历史；
- Human 的修改/Undo/Redo/Save/Play 暂时禁用，但选择、平移、查询可以继续；
- 只读 Scene/Project 资源附带 active transaction 状态，避免把临时结果误认为已保存结果；
- Human 可显式点击“取消 Agent 事务”，走相同 Rollback 能力并记录取消者；
- scene.save 在事务外、Commit 后另行调用。Commit 不隐式保存文件。

默认上限：64 个子命令、总生命周期 60 秒、捕获的作者态回滚数据预算 8 MiB。超限在执行新命令之前拒绝并自动回滚；snapshot 预算需要各内置命令提供有界估算/捕获入口，不能只限制 MCP JSON 字节。未知成本的命令不得加入事务。限制全部由 host 配置，预算不覆盖第三方库内部不可控分配。

事务只允许在主线程 Begin/Append/Commit/Rollback。主循环即使没有新请求也检查到期；client EOF、协议 worker 错误、主动断开或关闭 Editor 都通知主线程回滚。worker 不可自行 Undo。关闭过程先终止等待队列并 join I/O，再主线程完成事务处理；不可把清理任务排入已经停止且无人 Pump 的 dispatcher。

事务状态为 `Idle → Active → Committed/RolledBack`，补偿失败进入 RecoveryRequired。超时只在主线程可执行时生效，不是抢占式取消。非 owner/错误 token 的请求只被拒绝，不得取消另一个 owner 的事务。对于可确认属于 owner 的带正确 token 子命令，参数、权限或 Engine 执行失败都走统一 abort/rollback 路径，不能只处理 CommandBus::Execute 的失败而漏掉 JSON/schema 校验失败。未知 tool 或无法识别归属的 malformed request 只返回协议错误，既有事务仍受生命周期上限保护。

### 9.3 历史、dirty 和失败语义

Begin 保存初始 dirty 和 history cursor/redo tail。子命令成功后场景 provisional/dirty，但不增加 committed history，不裁剪 redo tail。

- Commit：非空 group 被 CommandBus 直接接管，生成一个 history entry；此时才丢弃旧 redo tail。dirty=true。空事务结束但不产生历史、不改变原 dirty。
- Rollback：子命令按逆序 Undo；全部成功后恢复 Begin 时 dirty、原 history 和 redo tail。不能通过公开 Undo 来撤销 pending group，以免碰到事务前的 Human 历史。
- 子命令执行失败：失败命令必须遵守“失败不遗留未记录 mutation”的支持条件；自动逆序撤销此前成功的子命令，结果包含原始失败和 rollbackOutcome。
- Commit 之前预留 history/group 存储，不能先丢 redo tail 再做可恢复验证；资源耗尽不作为常规成功回滚保证。
- 事务中的 CreateEntity UUID 与所有子命令 ID 保留，Commit 后一次 Human Undo 撤销整个 group；Redo 使用原 UUID 和原顺序。

CommandGroup 的 Undo/Redo 也可能在中途失败。Undo 失败时，应按正向 Redo 已撤销部分；Redo 失败时，逆向 Undo 已重做部分。补偿完成后保持 cursor 和原状态；不能只保持 cursor 却留下半个 group 的场景。

### 9.4 回滚失败与恢复

如果子命令/组补偿失败，进入 `RecoveryRequired`：保留错误、pending group、已执行/已撤销位置和事务前的受限作者态诊断摘要；禁用新的作者态修改、Save、Undo/Redo 和 Play。只读查询、日志、审计及 Human 的显式恢复操作保持可用。

不能宣称“已回滚”，也不能自动 Reload 丢掉用户事务前的未保存工作。v0.9 的最低恢复入口是 Human 明确选择“放弃当前未保存状态并重新打开磁盘 Scene”，先销毁绑定旧 Scene 的 host/history，再按正常加载链路重建；界面必须说明会丢失未保存状态。退出不会自动保存故障场景。事务测试必须覆盖正常完整回滚和注入失败后的隔离。

对 v0.9 白名单内置 Scene commands，在合法状态下的正常失败场景必须验证能完整补偿；`RecoveryRequired` 是不可兑现回滚时的显式故障出口，不是替代普通 rollback 的实现方式。

Terminal transaction 结果在当前连接保留最近 32 个，支持重复 Commit/Rollback 返回原终态，不重复修改。对同 ID 发出相反终态操作返回 InvalidState。普通 Scene mutation 不承诺跨断连 exactly-once；Agent 应先读取状态再决定重试，JSON-RPC request ID 不充当永久幂等键。

## 10. Audit / Agent Activity

Engine CommandBus 内置 Activity 存储，默认保留 2,000 条；描述/错误各限 1 KiB、最多 16 个 effect 摘要，并标注截断。它是工程诊断记录，不是持久、防篡改的安全审计系统。

记录：sequence、timestampMilliseconds、sessionId、actor、commandId、transaction、description、outcome、affected UUID/Reflection ID 摘要和错误。非命令操作的 description 为操作名；不保存原始参数。运行实例和失败帧的完整上下文由 RuntimeStatus 与 LogStore 提供。

- 记录 Agent Scene mutation、Save、Runtime Control、Transaction，以及拒绝/失败结果；普通查询默认不记录。
- 子命令 Pending、Commit、Rollback、Failed、RecoveryRequired 分开记录，不能把暂存修改显示为最终成功。
- Human Undo/Redo Agent 命令时，产生新的事件并引用原 command/group ID，不删除原记录；Actor 取当前操作者。
- 运行控制不是作者态 ICommand，不进入场景 Undo 历史，但仍有独立审计事件。
- Audit identity 由本地 host/connection 分配。MCP client 自报名称仅作为不可信展示文本，不作为已认证用户。
- 不记录完整 Lua 源码、任意文件内容、原始内存或无限参数。敏感路径显示相对项目路径；UUID/effects 过多时标注 truncation/count。
- 通过命令 receipts 获取精确效果，避免在 Editor/MCP 各维护一套 before/after 计算；请求拒绝、Save、Runtime 等无命令操作由 host 记录。

新增 `engine://agent/activity`，支持 after/limit/transactionId，沿用日志的有界游标语义。Editor Agent Activity 使用同一存储，显示结果、事务分组和对象定位；对象已删除时显示 UUID，不假设仍可选中。诊断缓冲满时淘汰旧记录并暴露 gap，不阻塞主线程。

## 11. MCP 能力目录与权限

| 新 Tool | 参数要点 | 成功含义 |
|---|---|---|
| runtime.play | 可选 startPaused，仅新运行实例 | 初始化完成/恢复完成，返回 RuntimeStatus |
| runtime.pause | 无 | 已暂停，之后无连续 simulation tick |
| runtime.stop | 无 | 已执行清理并返回最终状态；清理错误保留 |
| runtime.step | 无 | 已成功执行恰好一个固定 timestep |
| transaction.begin | label | 已取得作者态独占写 token |
| transaction.commit | transaction（UUID） | 已结束并成为一条可撤销历史，未保存磁盘 |
| transaction.rollback | transaction（UUID） | 已恢复事务前状态；失败绝不能报告成功 |

新增 Resources：runtime/status、runtime/entity/{uuid}、logs/recent、profiler/latest-frame、transaction/status、agent/activity，均使用 `engine://` 前缀。

新增实时 Resources 不允许沿用静态缓存提示；每次读取取当前主线程状态/最后完成快照，显式标注运行实例、帧号或 sequence。ResourceRegistry 对带 query 的 URI 应先解析到已注册的固定资源，再交由该资源校验白名单参数；不是任意 URI/file 路由。该适配必须保留现有 UUID templates 与无 query 资源的匹配行为。

资源读取保持无副作用；业务结果复用现有 modern/legacy JSON 编码与错误映射。Engine Error 不含协议 JSON。错误必须区分 InvalidState、NotFound、PermissionDenied、BudgetExceeded、RecoveryRequired，新增 ErrorCode 时避免改变既有值。

权限增加 RuntimeRead、RuntimeControl、DiagnosticsRead、TransactionControl、ActivityRead；事务内子操作仍校验 SceneWrite，不能凭 transactionId 越权。Commit 再校验当前操作权限；权限撤回导致不能提交时，执行受控回滚。

当前 ClassifyMcpOperation 把未知 Tool 默认归 ProjectRead，不能直接照搬到新增写工具：用显式工具/资源分类表或描述符字段，未知操作返回 Unclassified 并拒绝执行；catalog discovery 可单独归 ProjectRead。注册新增 handler 必须同时注册 operation，测试验证完整性。

保留本地 stdio 默认允许已暴露能力的 v0.8 策略，不借本版本增加 OAuth 或四级完整权限 UI。内部超时/断连补偿和 Human 取消是 host cleanup 能力，不能因客户端权限撤回而失去恢复能力。所有授权仍发生在主线程、业务处理之前。

协议继续支持 v0.8 的两种 era，不升级 transport、不手写第二套 handlers。stderr diagnostics 与 protocol-only stdout 保持不变。返回 JSON 大小沿用现有 transport 上限，列表/日志/trace 必须在编码前受限，超限明确返回截断元数据或可恢复错误。

## 12. 验收场景和测试策略

### A. 最小 Runtime Debug 闭环

使用测试项目中的 Lua 脚本，每次 OnUpdate 将 Transform.x 增加 `speed * dt`，不新增 Engine gameplay 字段或依赖真实键盘。

1. Agent 创建实体并配置 Sprite/LuaScript/Transform，保存。
2. `runtime.play(startPaused=true)`；读作者态 x 和运行态 x。
3. Step 三次；运行态帧号为 3，x 与已知 timestep 结果近似相等，作者态 x 不变。
4. Pause 期间普通 host tick 不推进；Resume 后恢复推进；Stop 后 Runtime 不可读，作者态和历史保留。
5. 注入固定 Lua 错误，进入 Faulted；读取 error/日志/Runtime；Stop，修正测试脚本并重新 Play 验证。

脚本修复可由测试驱动写入临时 fixture 或开发者常规代码工具完成，不能偷偷新增 MCP 任意文件写能力。

### B. Profiler 闭环

在相同 scene fixture 下验证 CPU scope 层级、simulation frame 关联、Scene/Game 两个 pass 的计数；Editor 和 MCP snapshot 内容一致。隐藏一个视图后状态为 unavailable，不能残留上一帧计数。

记录采样开启/关闭的相同工作负载结果、机器/构建配置、样本数和中位数/p95，作为基线；不在共享 CI 上设绝对毫秒阈值，不把 Debug 数字作为发布性能承诺。

### C. Transaction / Audit 闭环

Begin → Create → Add → Set → Commit → Save → Human Undo → Human Redo。检查一条 committed history、UUID 稳定、Camera.primary 副作用与子树删除恢复、Activity 的命令关联。

错误用例：中途错误参数/资产类型、失败命令、错误 token、另一个 owner、Human 写入冲突、Save/Play 冲突、64 条上限、snapshot 预算、超时、EOF、重复终态、rollback 故障、group Undo/Redo 补偿故障。

回滚成功时比较 Scene authoring serialization、dirty、history cursor 与 redo tail；不能只检查实体数量。临时文件在专用测试目录，测试不能改仓库 SandboxProject。

### D. 测试层次和完成条件

- Engine 单测：状态机、时钟、日志游标、scope 边界、分组/补偿、预算与事件；先失败测试后实现。
- Host 集成：真实 ProjectSession/McpEditorHost + FakeRenderDevice；线程、guard、dirty、资源生命周期、共享 Undo、关闭顺序。
- Python 子进程 E2E：扩展现有 JanusMcpExternalHost，调用生产能力完成 A/C，modern 和 legacy 都覆盖；测试宿主不升级为生产 Headless。
- 真实 Editor 冒烟：可见 Play/Pause/Step/Stop、故障现场、Console/Profiler/Activity、Agent 修改后的 Human Undo；记录一次真实 MCP client 的版本和配置。没有可用图形环境时如实记录缺口，不能以 fake renderer 冒充此项通过。
- 全量 Windows configure/build/CTest、git diff --check、生成文件 ignored；264 是基线，不是新测试数量目标。

完成时 README/路线图/AGENTS/本设计一起更新为 Implemented，记录 commit、测试结果、真实 Editor 验证和性能基线。只在全部 v0.9 必交能力成立后推进当前里程碑。

## 13. 开发路线

推荐严格按下列阶段交付，具体 PR 清单见配套计划：

1. Runtime 状态机和只读运行态；
2. 结构化日志 + MCP Runtime，完成最小 Debug E2E；
3. Profiler recorder + 两视图统计 + Editor/MCP；
4. CommandGroup + Transaction + 生命周期清理；
5. Audit/Agent Activity + 故障矩阵 + 完整收尾。

本方案不安排多人并行铺开模块。每一步都以可运行代码和测试为出口，不先提交大量不可调用的空接口。实施中若新增依赖、协议工具、磁盘副作用或扩展到 v0.10，须先更新范围说明。
